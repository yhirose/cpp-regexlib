# regexlib — 内部設計

`regexlib.h` の内部の仕組み。ユーザー向けリファレンス（構文・意味論・公開 API）は
[`reference.md`](reference.md)、本書はエンジン本体を扱います。

実装は**1つの実証済みベースライン**の上に重ねたアクセラレータ群です。**書記素
Pike VM**（subject を Unicode 拡張書記素クラスタに分割する Thompson NFA 仮想機械）
は正しいが遅い。より速い経路——leftmost-first 遅延 DFA、非ASCII 用 UTF-8 バイト
パス、bounded キャプチャエンジン、SIMD プレフィルタ、view ベース結果コンテナ——は
すべて、そのベースラインと**まったく同じ**結果を出さねばなりません。設計全体は、
証明可能に安全な場面では Pike よりはるかに速い経路で走らせつつ、この等価性を保つ、
という方針で組まれています。

譲れない2つの契約がすべてを形作ります:

- **線形時間 / ReDoS 免疫。** どのエンジンも無制限にバックトラックしない。非アンカー
  検索は単一前進パスで、候補ごとに再シードしない。
- **leftmost-first（Perl）意味論**を、全経路・全パターンで。

## 全体像（ひと目で）

パターンは一度だけバイトコードにコンパイルされ、各マッチ要求は、そのパターンと
subject に対してベースラインと等価だと証明できる範囲で最も安い経路に振り分けられます。
（図中ラベルは整列維持のため英語のまま）

```
  pattern
    |   compile (sec 3): lower the AST to NFA bytecode
    v
  Program(s):  byte program        (Op::Byte sub-automata, run by the DFA tiers)
               code-point program  (Op::Char/Class/Any, run by the Pike family)
    |
    |   match request on a subject:  test / search / find_iter / find_all
    v
  tier dispatch (sec 2):  is the pattern DFA-able? + is the subject simple?
    |
    +-- Tier 1  capture-free & DFA-able  -->  lazy DFA finds [s,e); no Pike   (sec 2,4,5)
    |
    +-- Tier 2  captures & DFA-able      -->  DFA finds [s,e), then a capture
    |                                         engine fills groups in the span (sec 6)
    |
    +-- Tier 3  lookaround / overflow    -->  grapheme Pike VM over the whole
    |                                         subject, helped by prefilters   (sec 7)
    v
  result delivery (sec 8):  MatchResult (one) | find_iter (lazy bulk) | find_all (eager bulk)
```

**実際にどのエンジンが動くか**は、パターンの形と subject の内容の両方で決まります:

| パターン | subject | 動くエンジン |
| --- | --- | --- |
| キャプチャ無し・DFA 可能 | ASCII（UnicodeScalar なら*任意*の subject） | 遅延 **DFA** — 高速パス（§2） |
| キャプチャ無し・DFA 可能 | 非 ASCII だが全クラスタが単一コードポイント | **EGC バイトパス** DFA（§4） |
| キャプチャ無し・DFA 可能 | 非 ASCII で実際に複数コードポイントのクラスタを含む | 書記素 **Pike**（§4） |
| キャプチャあり・DFA 可能 | （任意） | DFA が span を特定 → **キャプチャエンジン**（§6） |
| 後読み/先読み・入れ子の空ループ・キャッシュを断念した DFA（§2） | （任意） | 書記素 **Pike** — フォールバック（§2） |

書記素 Pike VM（§1）が唯一の実証済みベースラインで、他の行はすべて、Pike と
*まったく同じ*結果を返さねばならないアクセラレータです。§9 がその等価性の担保です。

### 決定の置き場所：`Plan` と呼び出しごとの状態

*パターンごと*に一度だけ決まるもの — コンパイル済みプログラム、tier 適格フラグ
（`dfa_ok_`、`byte_path_` など）、prefilter 状態（§7）— は、不変 struct
`Regex::Plan` に集約されています。Plan のコンストラクタが名前付きステージ
（`compile_core`、`analyze_core`、`plan_egc_byte_path`、`plan_assert_tiers` など）
で構築し、マッチ時のコードは `plan_.…` として読むだけです（マッチ系エントリ
ポイントはすべて `const`）。補助プログラムは `Plan::Compiled`（プログラムと
その `Match` pc の束。`ok()` が「このプログラムは構築済みか」に答える）として
保持します。呼び出しごとに変化する状態はすべて別の場所 — スレッドごとの
`FindCache`（§8）が持つ遅延 DFA キャッシュとスクラッチバッファ — にあります。

## 1. マッチモデル：書記素クラスタ

決定的な選択：**マッチの単位は Unicode 拡張書記素クラスタ（EGC）**（UAX #29）で
あり、コードポイントではありません。`.` はユーザーが知覚する 1 文字をちょうど消費
するので、`/.+/` を `"👨‍👩‍👧‍👦"` に当てると 1 要素にマッチします。マッチ位置は元の
UTF-8 subject への**バイトオフセット**で、常にクラスタ境界に揃います。

書記素分割は**状態依存**です——2つのコードポイント間に境界があるかは、その
`Grapheme_Cluster_Break` プロパティと周囲の並びに依存します。これがエンジンの独自性
と唯一の性能崖（§4）の両方の源です：バイトオートマトンはクラスタでなくバイトしか
見えません。

### セグメント化（`Segmented`）

```cpp
struct Segmented {
  std::vector<std::u32string> graphemes;  // 各クラスタのコードポイント
  std::vector<size_t> byte_begin;         // size == graphemes.size() + 1（末尾=終端）
  std::string_view source;                // 元の UTF-8 subject
  bool ascii = false;  // 全バイト < 0x80 → 書記素 index == バイト index
};
```

`segment()` には **ASCII 高速パス**（全バイト `< 0x80` → 各バイトが自身のクラスタ、
`byte_begin[i] == i`、デコード/分割なし）と**一般パス**（コードポイントへデコードし
各バイトオフセットを保持、`reg::unicode::grapheme_length` でクラスタにまとめる）があり
ます。`segment_cp()` は UnicodeScalar 用：1 コードポイント1エントリ——素の UTF-8
デコードで**書記素分割ではない**。Pike VM はどちらの `Segmented` でも変更なく走り
ます。

### クラス所属はベースコードポイントで判定

クラス / `\d\w\s\p{…}` はクラスタを**ベース（先頭）コードポイント**で分類します
——クラスタは表示上の 1 文字として振る舞います:

```cpp
bool matches(const std::u32string &g, bool icase) const {
  return g.empty() ? negate : matches_cp(g[0], icase);
}
```

よって `\w`/`\p{L}` は `é` を NFC（`U+00E9`）でも NFD（`e` + `◌́`）でもマッチし、
`\s` は CR-LF クラスタにマッチします。単一コードポイントのクラスタは自身がベース
なので、そこでは `matches_cp` と同一です——これが、`matches_cp` を直接呼ぶ
バイト/コードポイントエンジンが単一コードポイント入力で書記素エンジンと一致する
理由です。（このベースコードポイント規則は意図的な意味論選択で、旧「クラスは単一
コードポイントのクラスタのみにマッチ」規則は誤りでした。）

### パターン中のリテラルも書記素分割される

パターン中のリテラルはクラスタにコードポイントの**完全一致**（`lit_match`）でのみ
マッチし、ベースコードポイントでは判定しません——つまり厳密リテラルはクラスより
厳しい。これが予測どおりに振る舞うには、パターンのリテラルテキストも subject と
まったく同じようにクラスタへ分割される必要があります。タイプされたリテラルは既に
そうなっています（トークナイザがパーサにクラスタ単位で渡す）が、**エスケープ——
`\r`・`\n`・`\uXXXX`——はそれぞれ単一コードポイントのリテラルとして解析される**ため、
`\r\n` のようなエスケープ列は2つのリテラルのままとなり、subject が提示する分割不可能な
CR-LF クラスタ（UAX #29 GB3）に決してマッチできません。そこで `parse_concat` は
融合パス（`fuse_literal_graphemes`）を走らせ、隣接する未量化リテラルの最大連続を
書記素境界で再分割します。これにより `\r\n` は単一の `U"\r\n"` クラスタリテラルに
コンパイルされ——タイプされた等価テキストが生成するノードと同一になります。
（`\r\n?` の `\n?` のように量化されたエスケープは独立した atom で、融合されません。）
CodePoint モードではこのパスは no-op です——複数コードポイントのリテラルは、分離した
リテラルと同じコードポイント単位のマッチ列を発行します。

## 2. leftmost-first 遅延 DFA

**一言で：** 全スレッド同時実行の Pike VM の代わりに、決定性の状態機械（DFA）を
subject 走査に合わせて遅延構築する。ただしスレッドの*優先度*を保持するので、最長
ではなく Perl の leftmost-first マッチを返す。

Pike VM のホットコストは `add_thread` の ε-閉包（入力を消費せず到達できる状態集合）
＋キャプチャの copy-on-write で、Pike VM に構造的なもの——密マッチで RE2 に 1〜2 桁
劣ります。対策：**leftmost-first マッチを直接生む DFA**（RE2 / Rust `regex-automata`
の設計）。

これは**優先度順・match-cut** の遅延 DFA です。DFA 状態は NFA プログラムカウンタの
**順序付き**（優先度）ベクタで、**ソートせず** intern します（順序が状態同一性の
一部）。ε-閉包は Pike の `add_thread`（DFS 先行順、`Split.x` を `Split.y` より先）
を写しますが、キャプチャは持たず、**最初の `Match` で cut** します：到達した
`Match` より低優先のプログラムカウンタは捨てる（生きたマッチが後続の選択肢を殺す）。
あとは素朴な「最後の accept を記録」前進スキャンで leftmost-first 終端が出ます：
貪欲 `a+` は高優先の継続スレッド（最長 run）を保ち、lazy `a+?` や `a|ab` は cut で
止まります。

**longest-safe 述語はありません。** 旧 DFA は leftmost-*longest*（POSIX）なのに契約
は leftmost-*first*（Perl）だったため、静的述語が DFA で扱えるパターンを制限して
いました——不完全（DFA 可能な選択を弾く）かつ不健全（一部の可変オプショナル前置を
誤分類）。順序付き+cut DFA はスレッド優先度を表現するので、述語なしで任意パターンに
対し leftmost-first です。

**非アンカー性はプログラム内に**あり、位置ごとの再シード（開始位置間で優先度が
壊れる）ではありません：前進プログラムは `lf_prog_ = (?s:.)*? + pattern`、最低優先の
lazy 前置1つで、いずれかのパターンマッチが生きると match cut が除去します。バイト
オートマトン（US モード、バイト各 tier）では前置は**任意 BYTE**——任意コード
ポイントでは UTF-8 継続バイト単独を飛ばせないため。

### 開始位置の復元（逆 DFA）

DFA 状態は占有するプログラムカウンタの*集合*で、「どこで始まったか」を持ちません
（持たせると状態数が入力長に比例して増え DFA でなくなる）。だから前進スキャンは
マッチの*終端*は言えても開始は言えません。開始は、`e` から逆方向プログラムを左へ
走らせ最小の accept する `s` を記録する**逆バイト DFA** で復元します。逆 DFA は
**順序なし**（ソート）：「`[s, e)` はマッチか？」はブール到達性問題です。逆 *Pike*
は書記素 `Segmented` が必要で tier-1 の「分割なし」の利点を潰すため、バイト DFA に
します。

### 表の形：バイトクラス、行オフセット、バイト数の予算

1 ステップのコストは、そのステップが読む表で決まります。だから表は小さく、1 回の
読みで済むように作ってあります。

- **列はバイトごとではなく、バイトクラスごと。** プログラムのどの命令も区別しない
  2 つのバイトは、どの状態からも同じ遷移をするので、1 つの列を共有します。クラスは
  プランの構築時に、プログラムごとに 1 回だけ求めます（`byte_classes`。結果は
  `ByteClasses` として、`LazyDfa` が走りうる各プログラムの隣に持つ）。バイト
  オートマトンの命令列は歩きません：コンパイラが、出力したバイト範囲を控えておき
  （`byte_ranges`）、大きいクラスブロック（Unicode の `\w` は 5,000 命令で、重複を
  除いた範囲は約 470 個）は自分の範囲のクラスを一緒に持ちます（`ClassBlock`。
  ブロックをキャッシュする所で、プロセスにつき 1 回だけ求める）。プログラムの
  クラスは、それらをお互いと、ばらの範囲とで細分したものです
  （`refine_byte_classes`）。書記素プログラムは小さいので命令列を歩き、重複を除いた
  各オペランドに、受理する ASCII バイトを尋ねます（`ascii_mask`。書記素プログラムを
  バイト単位で進めるのは、主題が全部 ASCII のときだけです：`lazy_inst_matches`）。
  プログラム 1 本のクラスにかかるのは、最初の構築で約 0.5 µs。求めるのは `LazyDfa` が
  走りうるプログラムだけです（`plan_byte_classes`。リテラルだけのプラン、assert DFA
  だけのプラン、Pike だけのプランには何も求めない）。DFA は 256 バイトのコピーで
  受け取ります。
  `[a-zA-Z]+ing` は 6 クラス、Unicode の `\w` を含むパターンで約 100 クラス。
  クラス番号はバイト順に振るので、ASCII のクラスはどの行でも先頭の列になり、
  キャッシュライン 1〜2 本に収まります。以前の行は、パターンによらず 256 エントリ
  （1 KB）でした。
- **状態番号は、その行のオフセット。** すべての行を 1 本の配列に連続して置き、
  1 ステップは `tr[s + cls[byte]]`、つまり依存鎖の上ではロード 1 回です。掛け算は
  無く、加算もありません。走査は列を先に表の番地へ足しておき（これは何も待ちません）、
  コンパイラが行と列を 2 つのロードのあいだで足してしまわないようにしています
  （`REGEXLIB_OPAQUE`。マッチしない散文に対する `[a-z]+[0-9]` の判定で
  746 → 894 MB/s）。
  行の直前のエントリが状態のフラグ（accept、leftmost-first の確定、dead、「開始
  状態である」）で、走査はこれを依存鎖の外で読み、1 つのマスクで調べます。フラグを
  状態番号に詰めることは、意図的にしていません（依存鎖に AND が 1 つ乗り、実測で
  約 12% 遅い）。
- **状態の intern はハッシュ集合と連続領域。** 各状態のプログラムカウンタは、
  1 バイト単位の差分に詰めて格納します。Unicode クラスを含むパターンの状態は
  プログラムカウンタを数百個持ち、大きい DFA の重さの大半は行ではなくこちらです。
  `[a-q][^u-z]{13}x`（15,587 状態）は 1 状態あたり約 1,750 バイトから約 300 バイトに
  なり、595 KB のテキストの最初の走査（全状態をそこで作る）は 301 ms から 48 ms に
  なりました。
- **走査ループの中にプレフィルタを置かない。** 開始状態での読み飛ばし
  （`dfa_start_skip`）は、状態のフラグがそう言ったときにループが呼ぶ関数です。
  インライン展開すると、その先の検索器がループのレジスタを使い、ループはカーソルも
  表もスタックに置くことになっていました。

Sherlock のテキストの上で regexlib 自身の DFA だけを走らせた、変更前と変更後
（MB/s。プレフィルタなしの 2 パスの chain。1 行目はマッチが密、残りはマッチが疎か
無しで、ほぼ前向きの走査だけの時間）：
`\w+` 168 → 196、`[a-zA-Z]+ing` 337 → 792、`[a-q][^u-z]{13}x` 109 → 392、
`Holmes.{0,25}Watson|Watson.{0,25}Holmes` 617 → 887、
`[a-z]+ [a-z]+ [a-z]+ \.` 490 → 889。DFA をまず作らなければならないコールドな
`search()` は、おおむね 2〜3 倍（CodePoint モードの `/\*.*?\*/`：11.4 → 3.6 µs）、
Unicode クラスを含むパターンでは最大 6 倍速くなりました。

assert DFA（`AssertDfa` と、そのバイト版・逆向き版）は別の表現（257 または 129
エントリ幅の行。バイトごとに 1 列）のままです。ただし、状態が 1 本の配列の中での
行のオフセットであることと、入力の位置を先に番地へ足すことは同じです
（`AssertStateTable`）。ここではフラグが状態ではなく edge に付きます（境界が
accept するかどうかは、その次のバイトで決まるため）。そこで edge は 2 語の組に
しています（`AssertEdge`）。遷移先の行と、その隣のフラグで、フラグは誰も待たない
2 つ目のロードで読みます。以前のように行と同じ語に詰めると、ロードと次のロードの
あいだに AND が 1 つ入ります。マッチしない散文に対する `\b[a-z]+\d\b` の判定は、
id をマスクして掛ける形で 408 MB/s、行をマスクする形で 730、組にして 892 です。
LazyDfa の形をバイトクラスまで含めて当てた試作では、これらの変更の前の表に対して
前向きの走査が 1.3〜1.6 倍でした。いまの表にバイトクラスを足すとどれだけ伸びるかは
測っていません。

### tier ディスパッチ

パターンから構造的に選ぶ 3 つの tier:

| tier | 条件 | 動作 |
| --- | --- | --- |
| **1** | キャプチャなし ∧ DFA 可能 | 前進順序付き+cut DFA が leftmost-first 終端 `e` を、逆スキャンが開始 `s` を見つけ `[s, e)` を返す。**Pike なし。** ASCII 書記素 tier・UTF-8 バイト tier（§4/§5）・assert 対応 DFA 経由の `^ $ \b \A \z` を担当。対象：`\w+`、`[a-z]+`、リテラル、一般選択（`a\|ab`、`(?m)^…\|…$`）。 |
| **2** | キャプチャ ∧ DFA 可能 | lf DFA が `[s, e)` を特定し、キャプチャエンジンが群を `e` で**境界付けて**解決（§6）。全群がマッチ全体を囲むパターン（`(\w+)`）はこの tier に来ません：capture-free の双子として計画されます（§3「ルートのグループ」）。 |
| **2a** | キャプチャ ∧ assert-DFA 可能（`^ $ \b \A \z` + 群、例 `(\w+)$`、`\.([a-z]+)$`） | **assert 対応** DFA が `[s, e)` を特定（capture を剥がした版）、bounded バックトラッカ（`bitstate_bytes`、assert op を `empty_flags_cp` で評価）が群を解決 ―― これらを支配していた Pike を置換（`(\w+)$`: 5300→700 ns）。特定は書記素 assert DFA（ASCII subject）または**バイト** assert DFA（`ByteAssertDfa`：非ASCII EGC subject、または**US モードの任意 subject**――下記）で行う。 |
| **3** | DFA 不可（後読み/入れ子空ループ）、または DFA がキャッシュを断念したとき | subject 全体の Pike VM ＋ §7 プレフィルタ。フォールバック。 |

`dfa_ok_` =「regular」プログラム（後読みなし、`Op::Loop` なし）；`dfa_assert_ok_`
は加えて空幅アサーションを許可し assert DFA が処理。どちらも純粋に構造的。Tier 2a
は Tier 1 の assert-DFA 経路のキャプチャ版：assert を含むキャプチャパターン
（`dfa_ok_` でない）も Pike でなく DFA 特定の span を得る ―― バックトラッカが
アサーションを絶対位置で評価する（`$` = span 端でなく真の終端）ようになったため。

**バイト assert tier は EGC 非ASCII と US モードで共有。** `ByteAssertDfa` は
UTF-8 バイトプログラムを1コードポイントずつデコードし assert をコードポイント単位で
評価する ―― これは EGC 非ASCII subject（バイト == 書記素）と US マッチング
（コードポイント、書記素なし）の両方が必要とするもの。よって US は assert エンジンの
コピーを得ない：US の `^ $ \b` パターン（capture 有無問わず）は**任意**の subject で
`assert_byte_find_span` / `assert_prefix_find` / `ByteAssertDfa` を再利用し、同じ
prefilter・同じ `cp_prog_` bitstate capture 解決を使う。モード依存は
`assert_byte_path_ok` のゲートのみ（US: 任意 subject；EGC: 非ASCII かつ複数CP
クラスタ無し）。EGC-ASCII の書記素 assert DFA は別の高速路として残る。US で span が
bitstate を溢れる場合はコードポイント Pike へフォールバック。

**この tier での capture は US 専用。** `assert_cap_` は ASCII subject 前提で
`cp_prog_` を組む（`assert_find_ok` が `ascii_grapheme_ok` でゲートする）ので、
EGC の capture パターンは非ASCII subject では書記素 Pike のまま。そこではバイト
オートマトンの答えが書記素エンジンの答えではないからで、末尾が単独の UTF-8 先頭
バイトの subject がそれを露呈する（書記素エンジンはその不正バイトに独自クラスタを
与え `([^ ]+)$` にマッチするが、バイトオートマトンは継続バイトを要求してマッチ
しない）。この理由から `assert_byte_path_ok` 自身が `ncap_ == 0` ゲートを持ち、
どの階段もそれを継承する。以前は各呼び出し側に書き下されており、書き忘れた 1 箇所が
まさにこの段落の元になった。

### tier の正式名（ソース中の `[Tier: …]` ラベル）

上の番号付き tier は「どのエンジンが走るか」を表す。ある呼び出しをどの tier が
受け持つかは 2 か所で決まる。find 系のエントリポイント（`test` / `search` /
`find_all` / `find_iter` / `find_at`）は 1 つの共有の階段（次節）を上る。`match` は
位置 0 に固定されていて、プレフィルタが使えず、どの段も別のプリミティブになるので、
同じゲートの上に自分の階段を持つ。ソースの各分岐には `[Tier: …]` ラベルを付け、
（パターン分類 × subject 分類）の組ごとに正式名を1つ定める：

| ラベル | ゲート | 動作 |
| --- | --- | --- |
| `Literal` | `literal_only_` | memmem（+ Grapheme モードでは書記素境界チェック）；subject 分類なし |
| `LiteralAlt` | `literal_alt_` 非空 | Teddy 複数リテラルスキャン、見つかった fingerprint で始まるリテラルの順序付き verify |
| `AssertAnchor` | `assert_.anchor_gatefree` | memmem + ヒットごとの境界 & アンカーフラグ verify；任意 subject |
| `AnchoredOnePass` | `aop_.ok`（`^body$` / `^body` の検証形：assert なしの body を capture 剥がしで判定。素の `^body` のみ追加で cut 規則も要求——`onepass_body_ok`） | 位置 0 からの**1 回**のコンパクト決定的歩行（`anchored_onepass_try`、search / match / test で共有）——状態は自分の行のオフセットで表す（LazyDfa と同じ前掛け。1 バイトごとのロードは前のロードだけを待つ）。1 行は 129 エントリで、状態の accept フラグのあとに ASCII の 1 バイトにつき 1 列が続く。フラグは依存チェーンの外で読む。幅を 2 のべきにしないのは、多くの行の同じ列が 1 つのキャッシュセットに集まらないようにするため（主題を変えながら 128 桁を検証する場合：128 エントリの行で 262 ns、129 エントリで 140 ns）。末尾 `$` は「accept==n」比較（uncut テーブル。終端が確定するので body は alternation でも lazy でもよい：`^(a\|aa)+$`）。素の `^body` は leftmost-first cut テーブルを使い、cut 規則を満たす限り最終 accept が leftmost-first 終端そのもの。**任意 subject で健全**：歩行は非 ASCII バイトで、また CR-LF クラスタを分割し得るパターンでは `\r` でも bail する（`onepass_walk_bails_cr`）。capture 付きでも歩行がスパンを決める——`test()` と全ての不一致（ReDoS 入力に対する `^(a+)+$`）はこれで決着し、一致時のグループはそのスパン上で解決する。`^body$` の `+cap` はさらに先へ：`onepass_anchored_start_` により capture one-pass 歩行の候補が位置 0 のみになり、`^(\d{4})-(\d{2})-(\d{2})$` は 1 回の歩行で終端とグループを得る（bail は assert チェーンへ） |
| WordOnePass | `wop_.ok`（`\b body \b`、capture なし、先頭/末尾 atom が語のみ。末尾 `\b` 付きはさらに全 accepting 状態の出バイトが語バイトであること。末尾 `\b` **なし**はテーブルが cut 付きになるので body に cut 規則も要求——`onepass_body_ok`） | 候補ごとのコンパクト歩行：候補=非単語が先行する開始可能バイト。候補は短いスカラーの入口ランプのあと、ブロック単位で取る（`word_start_block`。スキャンの節を参照）。末尾 `\b` は最終 accept での次バイト 1 判定（accepting 状態 admission により厳密：通過した accept の直後は必ず語バイト） |
| `Dfa/US` | `us_ ∧ dfa_ok_` | `byte_prog_` 上のバイト lazy DFA（suffix/inner prefilter）；続いて **capture の有無を問わず**（`onepass_unbounded_`）候補＋unbounded one-pass 歩行——1 マッチ 1 歩行で、capture があれば終端とグループを、無ければスパンを得る（slot 0/1 は ncap に関係なくコンパイラが出す）。located-span chain の 2 走査を置き換える。歩行の途中にある非ASCII バイトは**局所的な** bail：chain がその 1 件だけを処理し、ドライバは次の find から戻る（§2「線形性」） |
| `Dfa/EgcByte` | EGC ∧ `egc_byte_path(text)` | バイト lazy DFA（icase-prefix / suffix / inner prefilter、融合 EGC リテラルスキャン）；one-pass 歩行と `+cap` は同上。ただし CRLF collapse プランは除く（`byte_walk_ok`：そのバイトプログラムは CR-LF の対を 1 要素と数え、歩行の表は 2 要素と数える） |
| `Dfa/Ascii` | EGC ∧ `dfa_ok_` ∧ ASCII subject | 書記素プログラム上の lazy DFA（バイト == 書記素）；`+cap` 同上 |
| `Assert/Ascii` | `dfa_assert_ok_` ∧ ASCII subject | `AssertDfa`（開始復元はキャッシュ済 `AssertRevDfa`）+ assert literal/prefix/suffix/word prefilter；`+cap`: assert 対応 bitstate |
| `Assert/Byte` | `assert_byte_path_ok(text)`（US: 任意 subject；EGC: 非ASCII simple **かつ capture なし**） | `ByteAssertDfa` / `ByteAssertRevDfa`、同じ prefilter；`+cap` は US 専用（上記参照） |
| `Pike` / `Pike/cp` | 常時（フォールバック） | `prog_` 上の書記素 Pike VM；US: `cp_prog_` 上のコードポイント Pike |

どちらの階段も適格な tier を上から試し、DFA がキャッシュを断念したら次へフォールスルーする。
`Pike` は全 tier が一致すべき証明済みベースライン（§9）。

### find の階段

`search`・`test`・`find_all`・`find_iter`・`find_at` は、以前はそれぞれ自分の
ディスパッチ階段を持っていました。同じ判断の写しが 5 つあり、手で揃えていました。
そして揃っていませんでした。EGC バイト tier には one-pass 歩行が無く（`é` が 1 個
ある主題や CR-LF 改行の主題では、`\w+` が 2 走査の chain で走り、ASCII tier の
~260 MB/s に対して ~160）、`test()` には suffix と中間リテラルの段が無く（散文
595 KB への `e[a-z]{3,}q`：真偽値としては 0.56 GB/s、find としては 33）、Pike を
走らせる前に候補まで読み飛ばすのは `search()` だけで、融合スキャンを持つのは
イテレータだけでした。どれも、たまたまそれを得た入口に能力が結び付いていた例です。
いまは階段が 1 つで、ある段は全部の入口にあるか、どこにも無いかのどちらかです。

**段**（`Rung`）と、それぞれが走査に必要とするもの：

| 段 | 走るもの | 必要なもの |
| --- | --- | --- |
| `Literal` / `LiteralAlt` / `AssertAnchor` | プランそのものが位置特定になっているもの。下へ落ちない | カーソル |
| `TextAnchor` | テキスト先頭に固定されたパターンは 0 でマッチするか、どこでもしない：`AnchoredOnePass` の 0 からの歩行が find の全部。群を読まない呼び出し側（capture-free のプラン、または `test()`）のための段 | カーソル |
| `Classify` | 主題を見て、それを受け持つ系統の段に立つ。上の段がプランの全部でない限り、Grapheme のプランはここから始まる | 主題の分類 |
| `FusedPrefix` / `FusedSuffix` | 融合 EGC リテラルスキャン（§4） | キャッシュ |
| `IcasePrefix` / `Suffix` / `Inner` | 候補＋検証のプレフィルタ（§7） | キャッシュ、予算 |
| `Walk` | 候補＋unbounded one-pass 歩行：終端と群を 1 回で | 予算、保存スロット |
| `Chain` / `AssertChain` | located-span chain：前向きに終端、後ろ向きに開始、そして群 | キャッシュ |
| `Bool` | `test()` 専用：最初の受理状態で止まる真偽値の前向きスキャン | キャッシュ |
| `Pike` | ベースライン。書記素 Pike はまず候補まで読み飛ばし（リテラル前置、Teddy、先頭バイト集合）、そこで bounded backtracker を試す | セグメント化 |

**系統。** 主題が決めるのは 1 つだけ、どのエンジンの**系統**が受け持つかです
（`Family`：CodePoint モードでは `Dfa/US` と `Assert/Byte`、Grapheme モードでは
`Dfa/EgcByte`（`(?i)` のプローブが使える場合と使えない場合）、`Dfa/Ascii`、
`Assert/Ascii`、`Assert/Byte`）。系統の階段のそれ以外はパターンで決まるので、
プランを作るときに 1 回だけ求めます（`ladder_plan`）。系統ごと・呼び出し側の種類
ごとの階段（`Plan::family_`。呼び出し側は 3 種類で、find・真偽値・短い主題への
真偽値。`ladder_caller` を参照）と、走査の始まる段（`Plan::start_`。CodePoint の
プランの系統は主題に依らないので、その走査は系統の最初の段からじかに始まる）です。
系統を定義する場所は `ladder_family` の 1 か所、find が主題のゲートを読む場所は
`ladder_classify` の 1 か所（先頭固定の `match()` は今も自分で読みます）、系統の中の
段の順序を書く場所は `ladder_pick` の 1 か所です（系統より前の段は系統のものでは
ありません。それ自体で位置が決まるプランやテキスト先頭固定のプランは `ladder_plan` が
そこから始め、融合スキャンは、主題が ASCII でない Grapheme の走査を `ladder_classify` が
そこへ置きます）。系統の中の順序：

- `(?i)` の前置、次に suffix スキャン、次に中間リテラル。capture-free の find は、
  稀なリテラルのプレフィルタを歩行より先に使う（プレフィルタは memmem のヒットから
  答えを出すのに対し、歩行は採算の規則に見切られるまで候補を歩くため）
- 歩行。続いて、capture があるときの中間リテラル（マッチごとに capture の走査が要る。
  歩行は 1 回で群まで出す）
- chain。assert の系統では、歩行、次に assert chain

**中断。** 先へ進めない段は理由を言います（§2「線形性」）。**局所的**——one-pass の
表に遷移の無いバイト：その 1 件だけを下の段（`Ladder::below`）が処理し、次の
ステップではまた歩行に尋ねます。**大域的**——予算、採算の規則：その段は走査の残り
すべてで手放され（階段の中のフラグで、戻すものは無い）、`ladder_pick` に尋ね直します。
断念した DFA はカーソルの位置から Pike へ降格し、点検できないクラスタに当たった融合
スキャンも同じく Pike へ降格します。融合スキャンが分類し直す（`ladder_unfused`）のは、
予算が尽きたときと、CRLF collapse 版が自分の対象でない主題に当たったとき（その主題は
たいてい通常の系統が処理できます）です。

融合スキャンは、進みながら主題を点検します。したがってその結論が成り立つのは、
点検の済んだバイトの上だけです。ところが候補の検証は、その先へ歩きます。検証の
結論は、成功でも失敗でも、検証が「調べた」バイトにクラスタの問題が無いときだけ
有効です（歩行の到達範囲に対する `egc_match_clean`）。そのときだけマッチを返し、
そのときだけ失敗した候補を読み飛ばします。それ以外は、カーソルの位置から Pike が
答えます（カーソルが越えるのは、返したマッチか、失敗が確かめられた候補だけです）。後半（失敗側）は、階段を共有するまで抜けていました。共有後、
fuzz を既定の 10 倍回したところ、イテレータだけでなく全ての入口で見つかりました。
`qaqbcd́z` への `q(?:a[a-z]+z|b)` は、位置 0 の検証が結合文字で止まり（Pike は `d́` を
基底の文字として扱う）、位置 0 のマッチの代わりに位置 2 の `qb` を返していました。

**呼び出し側が欲しいもの**によって変わるのは 2 点で、階段は変わりません。
`Want::Test`（真偽値）は同じプレフィルタの段を使いますが、どの段も、find が報告する
終端まで進まずに、最初に届いた受理状態で止まります（`dfa_forward_first`。suffix
スキャンは前向きに歩くこと自体をしない）。マッチの残りは主題と同じ長さになり得る
からです（`[^?]+\?.*`：答えは `?` の位置にあり、leftmost-first の終端は行末）。
そして find が歩行や chain を使う所では、スキャンします（`Rung::Bool`）。真偽値が、
使い道の無い読み飛ばしに代金を払わないよう、限度を 2 つ置いています
（`limits::kBoolSkipBytes`、`kBoolFloorBytes`）。主題が 64 バイト未満なら、中間
リテラルの段を外してスキャンします（23 バイトのパスへの `[^?]+\?.*`：段を通ると
48 ns、スキャンなら 15 ns）。また主題の長さに依らず、その段が床を探して後ろへ見るのは
32 バイトまでです——そこでまだ生きている前半部は、先頭まで後ろ向きに歩いたうえで
もう一度前向きに歩くことになり、スキャンなら 1 回で済むからです。（CodePoint モードの
真偽値用 DFA には、開始状態での読み飛ばしがそもそもありませんでした。595 KB への
`zqj` は、真偽値としては 0.67 GB/s、find としては 89 でした。いまはバイトプログラムの
読み飛ばしを持ち、それに見合う長さの主題のときだけ、スキャンごとに有効にします。）もう 1 点、
マッチは**受け皿**（sink）に渡します（`RowSink`：列形式の 1 行。`ResultSink`：
その場で組み立てる 1 個の `MatchResult`。`NoSink`：何も残さない）。こうすると、
どの入口も別の入口の形の代金を払いません。`search()` が、直前に書いた行から結果を
組み立てていたときは、store-to-load forwarding の失敗で、20 ns の呼び出しのうち
~3 ns を失っていました。

**1 ステップか、全部か。** ディスパッチは `ladder_step<All, Out>` の 1 つです
（カーソルだけで足りる段は `ladder_shallow`、歩行は `ladder_walk`、残りは `ladder_deep`）。
`find_iter` は `++` ごとに 1 ステップ進みます。`find_all` は同じステップを `All` を
立てて 1 回呼び、その下では、段がその場で次のマッチへ進みます——DFA は解決済み、
カーソルは手元——そして階段に尋ね直すのは、段が止まったときだけです。（マッチごとに
入り直すと、密な `\w+` で 12% 遅くなりました。歩行はさらに自分のループ
`onepass_fill_run` を持ちます。）

**1 ステップの find にかかるのは、その段のぶんだけ。** 短い主題への `search()` と
`test()` は、ほとんどが準備で、エンジンより前に走るものがエンジンを遅らせます。
共有の階段がこの 2 つに何も払わせないようにしているのは、次の 3 点です。

- 階段の状態は**値**（`Ladder`：段、歩行の 1 つ下の段、呼び出し側が欲しいもの、
  フラグ 1 語。6 バイト）で、
  どの遷移も値を受け取って値を返します。1 ステップの find（`find_once`）は、
  これとカーソルを自分のフレームに置き、コンパイラがそれをレジスタに溶かします。
  段がポインタ越しに触るオブジェクトだったとき、同じ階段は `search()` に 1 回あたり
  ~100 命令を払わせていました。
- 単独で答えを出せる段は、ほかの段が使うものを用意する前に試します。まずカーソル
  だけで足りる段（`find_once`。テキスト先頭に固定された歩行はここへインライン展開
  します。検証用パターンの 1 回の呼び出しは、その歩行がすべてだからです）。次に歩行
  （`find_rest`：予算と、スレッドローカルの保存スロット。DFA を読まないドライバの
  歩行は、取得に 35 命令かかるスレッドのキャッシュ無しで走ります：`scr_walk`）。
  最後に残りの段。
- パターンについての判断は、呼び出しごとには何もしません（上の、プランの階段）。
  Grapheme の走査が主題を 1 回見る処理（`ladder_classify`）も、1 ステップの find に
  インライン展開します。階段を値で受け渡す 2 回の関数呼び出しだったときは、20 ns の
  `test()` のうち 230 命令を占めていました。

呼び出しより長く生きる走査（`Finder`：`find_iter`、`find_all`、`find_at`）は、同じ
階段とカーソルを保持し、同じステップを踏みます。

### 線形性（O(n²) の罠）

非アンカー検索は候補ごとに再開してはなりません（候補ごとアンカー再試行は O(n²) で
長い subject で数百秒ハングしうる）。よって：前進 DFA スキャンは**単一パス**で中断
位置から再開；逆スキャンは**直前マッチ終端より左へ行かないようクランプ**（逆作業の
総和はマッチ長の総和で抑えられる）；マッチ後は確定した Perl 終端から前進再開。正味：
前進は各バイト1回、逆はマッチ長の総和、tier-2 キャプチャパスはマッチ窓内のみ。
線形。

候補+検証型の**プレフィルタ**（§7）は公認の例外で、リテラル候補ごとに検証をやり直し
ます——パターンの反復が自分の候補バイトを吸収できると二次的になります（`a[a-z]+0` ×
`aaaa…`：全 `a` が候補で、失敗検証のたびに重なる尾を再歩行）。よって該当サイトは
すべて**失敗歩行バイト予算**（`WalkBudget` 型；尽きると `kWalkBail`）を持ちます：
成功した検証はカーソルを
終端まで進めるので重ならず、控除されるのは**失敗**歩行のみ。予算（≈subject 1 本分）
が尽きたらその呼び出し/イテレータでは当該プレフィルタを恒久的に放棄し、上記の
単一パス機構へフォールバック——最悪でも subject 1 本分の無駄歩行が一度きり＝合計
O(n)。ガード済みサイト：融合 EGC 前置スキャン、ReverseInner 非吸収検証、(?i) 前置
プローブ検証、assert リテラル前置/接尾 finder、unbounded one-pass 候補ドライバ、
suffix tier の候補ループ（scalar 検証の absorb ベイルが候補毎 O(n) の DFA 逆走査に
再入する）、そして chain-capture 歩行（アンカー右の要素がアンカーバイトを吸収し得る
ため失敗歩行が重なり得る）。
1 つの走査は、その全ステップで**1 つの予算**を共有します（ステップ毎の予算は
マッチのたびにリセットされ O(マッチ数 × n) を許してしまう）。それ以外のプレフィルタに
予算は不要：検証が O(1)/パターン長で頭打ち（literal、Teddy、アンカーフラグ）か、
admission の形状ゲートが構造的に抑える（var-pre 接尾の 1 atom 規則、
`assert_word_find` の語ごと候補 1 つ）ためです。

unbounded one-pass 候補ドライバは同じ予算に**採算規則**を重ねます
（`WalkBudget::spend_profitable`）。候補＋検証型ドライバが単一パスの chain に勝つか
どうかはパターンでなく subject で決まります（`(\w+)\s+(\d+)` を key=value テキストに
流せば全候補がマッチし 1 マッチ 1 歩行、散文に流せば全単語が候補で全歩行が単語の
末尾で失敗）。失敗歩行ごとに、そのコストの chain-byte 換算見積りを課金します——
SIMD run skip は 1 回 `kRunCost`（セットアップ＋脱出の分岐予測ミス。失敗の高い部分）、
テーブル遷移は 1 歩 0.5 byte（候補ごとの歩行は互いに独立でパイプライン上で重なる。
chain の 1 本の依存連鎖とは違う）——そして課金が走査済み距離を超えた時点で
ドライバは bail します。ただし `kMinScan` 分の実証ウィンドウを先に与えるので、
短い subject は 1 歩行のレイテンシ形状を保ちます。走査は bail 位置から下の段で
続くため、損失はそのウィンドウ分で頭打ち、subject 1 本分にはなりません。

ただし「走査済み距離」が物差しとして正しいのは、chain ならその距離を歩いたはずの
ときだけです。リテラル prefix や疎な先頭バイト集合に導かれるドライバは、候補を chain と
共有します——chain の前向き DFA は、開始状態から、ドライバが使うのと同じ memchr で
読み飛ばします——ので、候補と候補のあいだではどちらも仕事をしません。距離を物差しに
すると、こういうドライバの課金は、越えるべき所で越えませんでした：散文への
`e[a-z]+s`（候補 13 個に 1 個がマッチで、残りはそれぞれ run 1 回の失敗）は、課金が
距離の 0.96 倍にとどまり、chain なら ~505 MB/s のところを ~395 MB/s で走っていました。
こういうドライバでは、両者を**候補ごと**に数えます（`spend_at_candidate` /
`matched_at_candidate`）：歩行は呼び出し 1 回の固定費と 1 バイトあたり 0.5 chain-byte、
chain はずっと小さい候補あたりの固定費と、失敗なら 1 バイトあたり 1、マッチなら 2
（終端を求める前向きと、開始を求める後ろ向き）。定数は実測です：全候補がマッチする
`e\w*` は候補あたり歩行 7 chain-byte・chain 10.9、失敗する `e[a-z]+s` の候補は 6.5 と
4.5。（この規則は、階段を共有する前は ASCII tier のもので、損もその tier だけの
ものでした。歩行が全ての系統に入ったことで、全ての主題に現れました。）

この bail は**大域的**です——走査の残りすべてでドライバは終わり
（`kWalkBail`）。歩行の途中にある非ASCII バイトは別の出来事で、別のコード
`kWalkLocal` を返します：one-pass テーブルにそのバイトの遷移が無いだけで、その先の
バイトについては何も言っていません。だから**局所的**です：歩行の 1 つ下の段がその
**1 件**だけを処理し（`dfa_chain_step` / `assert_chain_step`。capture のあるプランでは
中間リテラルの段）、次の find ではまた歩行に尋ねます。以前はコードが 1 つだったので、`é` が 1 個あるだけ
で subject の残り全部が chain に渡っていました：CodePoint モードの `\w+` は、中央に
`é` を 1 個含む 512 KB の ASCII 語列で ~270 MB/s（`é` 無しなら ~410）でしたが、今は
~410 です（50 語に 1 語が `é` を含む場合：~205 → ~390）。局所 bail は失敗歩行と同じ
課金に、何も生まなかった呼び出しぶんの `kBailCost` を足したものを、**ドライバが**
進んだ距離に対して課します——bail のあと chain が進んだ距離はドライバの手柄では
ない——ので、ほとんどの find が bail する subject（全語が非ASCII 文字で始まる）は
同じ規則に引っかかり、bail は大域に変わります。線形性の予算は使いません：続く
chain step は bail した歩行が読んだバイトをすべて読むので、局所 bail は chain が
どのみち行う仕事で抑えられます。

段の並びのなかでドライバが置かれる位置も、同じ勘定から決まります。capture-free の
find は suffix / ReverseInner プレフィルタ（§7）をドライバより**先に**使います——
プレフィルタは memmem のヒットから答えを出すのに対し、ドライバは規則に見切られる
まで候補を歩くからです。capture のある find はドライバが先です（1 回の歩行で群まで
得られる。プレフィルタの段は capture の走査が別に要る）。この順序は `ladder_pick`
のもので、全部の入口に共通です。入口ごとに階段があった頃は、イテレータだけが
どちらの場合もドライバが先で、CodePoint モードの `[a-q][^u-z]{13}x` では find の
半分がドライバの実証ウィンドウに費やされていました（suffix スキャンを先にして
~17 → ~33 GB/s）。

その前段として、ドライバ自身の仕事を減らす厳密な工夫が 2 つあります：失敗歩行は
最初の restartable な run の終端を報告し（`CpOnePass::State::restart_ok`：ループ
する全バイトが開始状態からもその状態に入るので、run の途中から始めた歩行は run に
最初に入った歩行と収束する——それが失敗したなら全部失敗する）、位置スキャンは次の
バイトではなくそこから再開します。

### セーフティネット：DFA キャッシュの予算

regular なパターンでも、DFA の状態数は指数的に増えることがあります（`.*a.{18}` は
2¹⁸ 状態）。そこで遅延 DFA のキャッシュ（表と、intern した状態）には上限を置きます：
`limits::kDfaCacheBytes`、DFA 1 個あたり 8 MiB（中身の量。vector の伸長ぶんの余白は
別）。以前の上限は状態数（65,536）で、表だけで 64 MB、状態ごとのリストまで数えると
100 MB を超えていました。

**満杯になったキャッシュは、捨てずにクリアして詰め直します。** 走査はいま居る状態
から続き、DFA は主題がいま使っている状態の上で走り続けます。クリアは走査からは
見えません。ただし走査は、ミスのあとで 2 つのものを読み直す必要があります：表の
アドレスと、（フラグ経由で）どの状態が開始状態か（開始状態はその場で作り直します）。

**DFA が断念するのは、詰め直しが引き合わないときだけです。** 走査は進めたバイト数を
報告します。キャッシュを `limits::kDfaMinClears`（3）回詰め直したあと、ある 1 回ぶんが
「作った状態 1 個あたり `limits::kDfaMinBytesPerState`（10）バイト未満」しか進めて
いなければ、状態を作る速さがバイトを読む速さとほぼ同じ、ということです。そのとき
DFA は次のミスで `kCap` を返し、以後ずっとそうします（作ってある遷移は使えます）。
段はカーソルの位置から Pike VM に降格します。（この規則は RE2 と `regex-automata` の
ものです。詰め直しと Pike のどちらが得かはパターンによります：CodePoint モードの
`[ae].{20}[ae]` では、状態 1 個の構築が約 1.9 µs、Pike が 1 バイト約 50 ns なので、
釣り合うのは 1 状態あたり約 40 バイト。小さい ASCII のパターンでは 7 バイト前後です。）

assert DFA にも同じ予算があります（表の edge と、内部に持つ状態集合を数えます。
`AssertStateTable::full`）。規則はもっと単純で、いっぱいになった表は消さずに残し、
状態をそれ以上足しません。作った分はそのまま使われ、新しい状態が要る遷移は `kCap`
を返して、走査はキャッシュなしの対に落ちます。（こちらも以前の上限は状態数
（65,536）で、しかも上限を超えた表が、ミスに届く走査のたびに状態を 1 つずつ足して
いました。`\b[ab]*a[ab]{18}\b` を 4 KB の主題に 4,000 回かけると 293 MB を持ち、
まだ増えていました。今は 13 MB です。）

## 3. コンパイラとバイトコード

コンパイラは AST を NFA `Program` に下げます。形を決めた2つの圧力——**コンパイル
時間**と**プログラムメモリ**——はどちらも Unicode クラス（`\w`、`\p{L}`、数百の
UTF-8 バイト範囲列に展開）が支配します。

### ルートのグループ

AST を誰かが読む前に、パターン**全体**を包むグループをルートから剥がします
（`peel_root_groups`）。ルートにあるグループは、パターンが何にマッチするかに
何も足しません：

- 非キャプチャのもの——`(?:\w+ing)`——は純粋な構文で、常に剥がします。
- キャプチャするものが記録する span は、位置からしてマッチそのものです。剥がすのは
  パターンの**全ての**群がそういう包みであるとき——`(\w+)`、`((x))`、`(?:(\w+))`、
  `(?<n>\w+)`——だけで、そのとき `ncap_` は 0、`alias_groups_` が群の数を持ちます：
  パターンは **capture-free の双子**として計画・実行され、結果を渡すところで各群を
  マッチ全体として報告します（単発の結果は `finish_result`、`find_all` の行は
  `alias_rows`、`MatchIter` は 1 ステップごとに 1 行を広げる）。ほかに群があるなら
  包みのスロットは実際の仕事なので、残します。

これを AST の上で、どの解析よりも前に行うのは、解析がルートの**形**——リテラルで
終わる `Concat`、裸のリテラル列——を読むからで、プランまで残った包みはそれを
隠します。以前は、包まれたパターンはプランナにとって別のパターンでした：
`([a-zA-Z]+ing)` と `(?:[a-zA-Z]+ing)` は ~350 MB/s（`[a-zA-Z]+ing` は ~2700）、
`(Sherlock)` はリテラル tier の半分の速度、`([a-q][^u-z]{13}x)` は CRLF テキストで
書記素 Pike に落ちて 9 MB/s（collapse 経路が capture-free 限定のため。双子は
~20000）。今はどれも双子の速度で走ります。`find_iter` では完全に同じ、`find_all`
は行を広げる 1 パスぶんを払います（密な `(\w+)`：~330 MB/s、`\w+` は ~395）。

### 命令（`Inst`）——16 バイト・自由に再配置可能

```
Char  Class  Any  Byte        // 消費
Split Jmp  Save  Loop         // 制御フロー（Loop = 空ガード後退辺）
Look                          // 零幅後読み（subs[x]）
AssertBOL AssertEOL AssertWB AssertNWB AssertBeginText AssertEndText AssertEndTextNL
Match
```

`Inst` は**16 バイトかつ trivially copyable** です。重いオペランド——リテラル文字列
（`std::u32string`）、文字クラス（`CharClass`）、後読み本体（`Program`）——は命令に
**入れず**、所有する `Program` の out-of-line プールに置きます:

```cpp
struct Program {
  std::vector<Inst> insts;
  std::vector<std::u32string> lits;            // Char リテラル
  std::vector<CharClass> classes;              // Class オペランド
  std::vector<std::shared_ptr<Program>> subs;  // 後読み本体
  int nslots = 2;                              // 群あたり2、群0=全体マッチ
};
```

命令は小さな index のみを持ち、どのオペランド index も制御フロー先と共存しないため、
すべて **`x` スロットに重ねます**（op が意味を選ぶ）：`lit_idx()`/`cls_idx()`/
`sub_idx()` は `x` を読み、`Byte` は `[lo,hi]` 境界を `x` にパック。`op` を `uint8_t`
にし所有メンバを持たないので、構造体は 16 バイトの POD です。これが、大きな Unicode
クラスのバイトオートマトン構築を、命令ごとの構築/移動/破棄なしの **`memcpy`** に
する鍵です。定常スループットは `Inst` サイズに鈍感（バイト DFA は遷移表で走り、
ホットループで `Inst` を読まない）なので、効くのは必要だった所——コンパイル時間と
メモリです（`\w+` バイトプログラム：160→32→16 バイト縮小で 359 → 159 KiB）。

### UTF-8 範囲コンパイル

US モードとバイトパスでは、クラス / `.` / `\d\w\s\p{…}` は**バイト副オートマトン**
です。コードポイント範囲 `[lo, hi]` は UTF-8 バイト範囲*列*の集合へコンパイル
（Russ Cox の `utf8_ranges`：UTF-8 長境界で分割、次に先頭バイトが変わる所で分割）。
あるコードポイントが `[lo, hi]` に入るのは、その UTF-8 バイト列がちょうど1つの列に
一致するとき——よってバイト DFA は Unicode クラスを**デコードなし**でバイトを進める
だけでマッチします。`build_class_block` は1集合を `Byte` 連鎖の選択として出力し、
**`Split`/`Jmp` のみが先を持つ**（`Op::Byte` は fall-through で進む）ので、base 0 で
組んだブロックは `Split`/`Jmp` 先を再ベースするだけで*任意*オフセットに追加可能——
16 バイト `Inst` が買う再配置可能性です。

### クラスコンパイルのキャッシュ

Unicode クラスは現れるたび同じ数百範囲に展開され、1つの `Regex` が各クラスを複数回
出力します（前進+逆プログラム、出現ごと）。*ソース*クラスをキーにする `static`・
mutex 保護の3層メモ（ルックアップは展開でなく述語に比例）:

1. **`enum_cp_ranges`** — `\p{…}`/述語 → コードポイント範囲。`0..0x10FFFF` を一度
   走査（サロゲート除外）、述語でキャッシュ。
2. **`utf8_ranges_cached`** — コードポイント集合 → UTF-8 バイト範囲列。正規化集合で
   メモ化、方向独立。
3. **`class_block_cached`** — 出力済み `Inst` ブロック全体を `(集合, 方向)` でメモ化。
   以降の出力は `memcpy` 追加＋先の再ベース。

合わせて Unicode クラスのコンパイルを支配的コストからブロック `memcpy` に
（コンパイルベンチで ~12〜14×、`\w+` 0.44 → 0.037 ms）。

### 2プログラム分割

Unicode モードのパターンは1つの AST から最大2プログラムを出力:

- **バイトプログラム**（`Op::Byte` 副オートマトン）バイト DFA 用——大きい（クラスが
  UTF-8 副オートマトン）が文字ごとに再走査しない；
- **コードポイントプログラム**（`cp_prog_`、`Op::Char`/`Class`/`Any`）Pike 系
  エンジン用。Unicode クラスは*単一*の `Op::Class`（1 コードポイントをデコードして
  判定）——小さく、backtracker / one-pass キャプチャエンジンがバイトオートマトンの
  サイズを払わない。

オペランドプール分割により両者がまったく同じ `Inst`/`Program` 型を共有します。

## 4. 非ASCII の崖と EGC バイトパス

どの DFA tier もバイト/コードポイントオートマトンなので、歴史的に subject 全体の ASCII ゲートが
*あらゆる*非ASCII subject を全 DFA tier から書記素 Pike へ落としていました——~6× の崖
（密 `\w+`：`é` 1つで 58 → 9 MB/s）。実世界の散文では引き金はより微妙で、**CRLF 改行**
——各 `\r\n` が1クラスタ（UAX #29 GB3）——が subject 全体を書記素 Pike（~24 MB/s）へ
押しやっていました。

**鍵となる観察：subject 内の全クラスタが単一コードポイントのとき、書記素単位と
コードポイント単位のマッチは一致する**——よって UTF-8 バイト DFA は分割なしで書記素
エンジンとまったく同じ結果を出します。regular（`dfa_ok_`）パターンでは、書記素
プログラムと並べてバイトプログラム（`byte_prog_`、`byte_rev_prog_`、`byte_lf_prog_`）
をコンパイルし `byte_path_` を立てます。順序付き+cut バイト DFA は任意 `dfa_ok_`
パターンに対し leftmost-first——longest-safe 述語なし、ASCII と同様。

### `simple_from` — subject ごとのゲート

`egc_byte_path(text)` が subject ごとに判定。最初の非ASCII バイトまで（ベクトル化）
スキャンし、純 ASCII subject は安い ASCII tier へ抜け、非ASCII subject は残りだけ
チェックを払う。`simple_from(s8, start)` は subject に**多コードポイントクラスタが
ない**（=コードポイント≡書記素、バイト DFA の答えが書記素エンジンと一致）とき true。
単一前進パスで：ASCII 前置を `CR×LF` 融合についてチェック；`start` から、隣接2
コードポイントが融合した瞬間に棄却（`gb_fuses`）；**印字可能 ASCII ラン を SIMD で
スキップ**（印字可能 ASCII ランは多コードポイントクラスタを含めない）。融合があれば
書記素 Pike へフォールバック。

### CRLF — 崖と `crlf_byte_safe`

`simple_from` は全 `\r\n` を棄却するので CRLF 散文はバイトパスに乗りませんでした。
しかし CR-LF クラスタが問題になるのは、*パターン*が1クラスタ CR-LF と2バイト
`\r``\n` を区別できるときだけ。多くは区別できません。`crlf_byte_safe(node)` は構造的
述語——どの要素も差を観測しなければ安全:

- リテラルは `\r`/`\n` を含まない；
- クラスは `\r` も `\n` も**どちらもマッチしない**、または**両方**マッチするが
  無制限貪欲反復の直接被反復 atom としてのみ（貪欲 run は `\r` を `\n` を2バイト
  ステップで、書記素エンジンが1クラスタで消費するのとちょうど同じ位置で消費——
  同じ span、間に境界なし）。`\r`/`\n` の**ちょうど一方**にマッチするクラスは
  乖離し不安全；
- `.` は dotall 時のみ `\r`/`\n` に触れ、そのとき透過的のみ；
- **Multiline** の `^`/`$` は `crlf_inert` なパターンでのみ可。これらは何も消費
  しないが、multiline のアンカーは行終端*に*束縛し、ASCII tier はそれを任意の
  改行バイトで発火させる——よって CR-LF ペアの中では2つのコードポイントの**間**にも
  束縛する。1クラスタとしか見ない書記素エンジンには無い位置で、バイト側のアンカー
  集合は書記素側の上位集合、余分はちょうどクラスタ内部である。これは
  パターンのどの要素も単独の `\r`/`\n` を消費できないとき（`crlf_inert`）無害:
  そのときマッチは内部から開始できず（`\n` を消費する必要がある。空マッチは別途
  排除済み）、そこで終了もできず、跨ぐこともできない（どちらも `\r` を消費して
  いる必要がある）ので、余分なアンカーが撒くスレッドは accept 前に死ぬ。
  `(?m)^\w+` は高速 tier に残り、`(?m)(\s+)$` は残らない。後者を
  `"ab\r\n01 x\r\n"` に当てると書記素エンジンは1件（末尾クラスタ）、バイトエンジンは
  2件で、しかも `\s+` を最初のクラスタの内部で止める（Multiline でなければ
  テキストアンカーで、内部位置には一切触れない）。リテラルの `\r\n` ペアは上の
  リテラル規則では許容されるが inert ではない: この判定は内部に到達するかであり、
  ペアを消費することは到達することだから；
- 透過性は群境界、固定回数/非貪欲構造で止まる。

`can_match_empty_`（nullable）は CRLF 許容に**非空**マッチを追加要求します（空マッチ
がクラスタ内部の LF に落ちうる——バイトモードには在るが書記素モードには無い位置）。

`simple_from_crlf_ok` は `simple_from` ＋「CR×LF クラスタを許可」で、ASCII ラン全体
（`\r\n` 改行を含む）を次の非ASCII バイトまで SIMD スキップします。

リテラル規則自身に落とし穴があります: ペアは byte-safe ですが**書記素プログラムでは
safe ではありません**。パーサは `\r\n` を1書記素に融合し（`fuse_literal_graphemes`）、
*書記素*プログラム（`prog_`・`assert_lf_prog_`、`cp=false` でコンパイル）はリテラルを
「コードポイント列全体を intern した1個の `Op::Char`」として持ちます。つまりペアは
そこでは2コードポイントの単一ユニットで、その上の DFA は**バイト**を刻む——
どのバイトにも一致せず歩行が死にます。`crlf_byte_safe` がペアを許すのはバイト
プログラム（自分の2バイトとして素直にマッチする）向けの話なので、
`crlf_byte_safe_` と書記素プログラムを組み合わせる唯一のゲートである
`ascii_grapheme_ok` は追加で `!crlf_fused_lit_` を要求します。`cp_prog_` と one-pass
表は対象外です: それらは `cp=true` でコンパイルされ、`emit_cp_lit` がペアを
1コードポイント1命令に割ります。
これが無いと `\r\n$` を `"x\r\n"` に当てて書記素 Pike が `[1,3)` を返すのに no-match と
なり、`(\r\n)$` はエントリポイントが割れて `search` / `find_all` / `find_iter` が
`[1,3)` を返す一方 `test` だけが不一致でした。

失格したパターンが Pike ではなくバイト tier に着地するよう、2つのバイト側ゲートが
対になる例外を持ちます。`egc_byte_path` は `byte_path_` パターンのために純 ASCII の
CRLF subject を許容し、`assert_byte_path_ok` は assert パターン（`byte_path_` を
持たないので前者を使えない）のために同じことをします——条件も理由も同じ
（`crlf_byte_safe_ && !can_match_empty_`）。後者が無いと `\r\n` リテラルを持つ assert
パターンは書記素 Pike まで落ち、512 KB の純 ASCII HTTP ヘッダに対して
`\b\w+\r\n` の `find_all` が 14.0 MB/s、`\r\n$` の `search` が 550 ns でした
（有りなら 283 MB/s・74 ns）。

§7 のプレフィルタと合わせ、`/Sherlock/` を ~24 → ~13000 MB/s にしました。

### `crlf_collapse` — bounded な `\r\n` クラス反復

`crlf_byte_safe` は両方マッチ（`\r`/`\n`）クラスを*無制限貪欲*反復の atom（CR-LF の
*ラン*）としてのみ、しかも一度に 1 つだけ許容します。2 つのランが隣り合うと——直接でも、
空にマッチできる要素を挟んでも——バイトプログラムはペアの*内側*に境界を持てますが、
グラフェムエンジンにその境界はありません（`crlf_run_ends`。`t[^.]+[^q]+\.` は
`t\r\n.` にマッチし、`([^.]*)[^.]+,` は 2 バイトの間でグループを閉じていました）。
そのため、そういうパターンも byte-safe ではありません。また **bounded / lazy** 反復
（`[^"']{0,30}`、`[^u-z]{13}`）は CR-LF を 1 クラスタ vs 2 バイトと数えるため棄却します——これが（CRLF の）Sherlock corpus で最も負けた
パターン（`["'][^"']{0,30}[?!.]["']` が ~15 MB/s）です。**キャプチャ無し**かつ
`\r\n` に触れるクラスがすべて**否定クラス**なら、各クラス `C` を `(?:\r\n | C')` に
書き換えます（`C'` は `C` から `\r`/`\n` を除外＝否定レンジ集合に追加）。`\r\n` 枝が
CR-LF ペアを 1 要素として消費し（書記素エンジンの 1 クラスタ歩進に一致）、CR-LF を
消費する**唯一**の枝なので分割パースが存在せず、collapsed バイトプログラム
（`byte_prog_` / `byte_rev_prog_` / `byte_lf_prog_`、collapsed AST からコンパイル）は
ペア CRLF subject 上で書記素エンジンを再現します。`egc_byte_path` はこの subject を
`no_lone_crlf` でゲートして許可：lone な `\r`/`\n` は collapsed プログラムでマッチ
不能なので、全 `\r\n` がペアである必要があります。

キャプチャ無し限定——キャプチャありだとバイト DFA は span を書記素単位（CR-LF=1）で
確定しますが、グループは `cp_prog_`（コードポイントプログラム、CR-LF=2）で解決する
ため、CR-LF をまたぐ bounded グループは span を再マッチできずマッチ脱落します。
よってその種は書記素 Pike に留めます。これで `["'][^"']{0,30}[?!.]["']` は ~15 →
~740 MB/s（RE2 超え）。`[a-q][^u-z]{13}x` も崖を脱します（~7 → ~50 MB/s）が、残余の差は
`.{13}` の DFA 状態爆発であって崖ではありません。

collapse パターンが**必須の接尾アンカー**を持つ場合、per-call のゲート
（`simple_from_crlf_ok` + `no_lone_crlf`、接尾 prefilter 自身のパスに先立つ 2 回の
O(n) パス）を接尾スキャン自体に融合します（`egc_fused_collapse_ok` →
`egc_literal_fused_find` の `collapse=true`）。クラスタ条件はスキャンの非ASCII停止に
相乗りします。lone CR/LF 条件はそもそも**スキャンしません**：lone な CR/LF が問題に
なるのは collapsed バイトプログラムが実際に*歩く*場所だけなので、候補ごとの検証が
踏査した窓だけを調べます（`crlf_pairs_ok_window`——DFA 逆走査は踏査した床を、前方
再展開は到達点を報告し、窓は 1 バイト広げて縁をまたぐペアを実際の隣接バイトで判定）。
候補間のギャップは lone CR/LF を無害に含んでよく、ギャップスキャンは安い素の述語の
まま、subject は 1 回しか読みません。（collapse 済みのプログラムを走らせる suffix の段は、
ゲート付きの段も含めてすべて、候補の検証に `collapse` を渡します：
scalar 検証はバイトを数えるので、歩行が CR や LF に当たる候補は DFA に任せる必要が
あります。）不適格な窓（lone CR/LF＝ごく普通の Unix 改行
テキストがマッチ近傍にある）や融合クラスタは、主題を先に分類する系統へ bail し
（`ladder_unfused`）、Pike へは降格しないため、素の LF テキストは従来通り
ASCII DFA tier に乗ります。var-pre の接尾は scalar chain 検証が担う場合に許可されます
（終端を正確に計算し、検証済み窓の外への前方再展開が無い）。CRLF Sherlock corpus の
`[a-q][^u-z]{13}x` を ~7.7 → ~11.8 GB/s に（rure ~12.9）、窓の局所化で否定クラスの
引用パターンを ~11.5 → ~14.8 GB/s に。

### assert バイト tier

`\b`/`^$`/`\A\z` パターンは `dfa_assert_ok_`（`dfa_ok_` でない）で assert 対応 DFA が
処理。同じ EGC バイトパスを構築：コードポイント対応 `ByteAssertDfa` が非ASCII subject
を assert DFA に通し、`crlf_byte_safe_` / `can_match_empty_` ゲートを再利用します。
同じ DFA は CodePoint モードでも任意の subject を処理しますが、規則のうち 1 つは書記素
エンジンだけのものです：multiline の `^` / `$` は CR-LF の `\r` と `\n` の*間*では
成立しません（ペアは 1 クラスタで、内側に位置が無い）。CodePoint モードではペアは
2 文字で、その位置は行の終わりであり次の行の始まりなので、この例外は単位で切り替えます
（`bflags`）。

### 書記素 Pike に残るもの

真に多コードポイントクラスタ——結合マーク、ZWJ 絵文字、ハングル jamo、地域指標旗、
`Prepend` ラン——を含む subject は `simple_from` で落ち、分割が状態依存で正しい書記素
Pike で走ります。この残余崖は本質的（状態依存の書記素 `.` のバイトオートマトンは
存在しない）；§5 が逃げ道です。

**pure-ASCII subject の CR-LF。** ASCII 高速路は「バイト ≡ コードポイント ≡
クラスタ」を前提にしますが、これは CR-LF ペア（GB3 で 1 クラスタだが 2 バイト）を除く
全 ASCII バイトで成立します。ASCII を書記素モデルと一貫させるため、`segment()` は
`\r` を含む ASCII subject を書記素経路に回し（ペアを融合）、`ascii_grapheme_ok()` が
非ASCII byte path と同じ `crlf_byte_safe_ && !can_match_empty_` 述語で ASCII DFA /
assert tier をゲートします：CRLF 敏感パターン（計数付き `\r\n` クラス反復・dotall
`.{n}`・nullable 本体・multiline `^`/`$`）は ASCII-CRLF subject で CR-LF 融合する Pike
に委譲。`.` の特別扱いは不要です——非dotall `.` は元々 `\r\n` を除外するので byte path
も書記素エンジンも CR-LF の手前で止まり一致し、`Holmes.{0,25}Watson` 等の近接パターンは
byte DFA に残って全速。唯一の食い違いは CR-LF 内部 LF 位置の空マッチで、`!can_match_empty_`
で除外されます。

## 5. UnicodeScalar モード（バイトオートマトン）

`CodePoint` マッチ単位（`reg::set_default_match_unit`）はマッチ単位を **Unicode
スカラ（コードポイント）**——RE2 / Rust `regex` のモデル——に切り替え、崖を完全に
除去：バイト DFA が生の UTF-8 を分割
なし・ASCII ゲートなしで直接走ります。構文・leftmost-first 意味論・線形時間・
バイトオフセット報告は不変；変わるのは `.`/クラスの単位とオフセット境界だけ。

§3 の**2プログラム**（`prog_`/バイト + `cp_prog_`/コードポイント）を保ちます。
`run()`/`run_saves()` はプログラムでパラメタ化され、実証済み書記素 Pike が `cp_prog_`
を変更なくコードポイント意味論・バイトオフセットで走らせ、subject は `segment_cp`
（素の UTF-8 デコード）で供給します。

### コンパイル時の大文字小文字畳み込み

バイト DFA はバイト単位で畳めないので、icase はコンパイル時にバイトプログラムへ焼き
込みます。`case_fold_groups` が `0..0x10FFFF` を一度走査（キャッシュ）し
`simple_case_folding` でサイズ≥2 の軌道（`{a,A}`、`{k,K,U+212A}`）にグループ化；
`case_expand` がリテラル/クラスと交わる軌道の全メンバを追加——`prog_` が全大小変種を
直接受理し、Pike が `cp_prog_` 上でマッチ時に適用するのと同じ畳み込み等価
（`fold(a)==fold(b)`、軌道含む）に一致します。（`ß`→`ss` の完全畳み込みは書記素
エンジン同様 対象外。）

DFA ベースのエンジン（バイト DFA、one-pass）は US（任意 subject）と ASCII 書記素
モードに適用できますが、分割が状態依存の非ASCII *書記素*マッチには適用できません。
よって US が非ASCII の高速パスで、非ASCII 書記素キャプチャは書記素 Pike に残ります。

## 6. キャプチャエンジン

順序付き+cut DFA が leftmost-first `[s, e)` を特定し、群はその span 内（`e` で境界
付け）を**コードポイント**プログラム `cp_prog_` 上で最も安い能力あるエンジンが解決。
速い順に 3 つ:

| エンジン | 発動条件 | 仕組み |
| --- | --- | --- |
| **CpOnePass**（`build_cp_onepass`） | パターンが one-pass・span が全て単一コードポイント | 決定的キャプチャ記録 DFA：pc 集合状態、各遷移が `(次状態, 現在位置にセットするスロットのビットマスク)` を持つ。群 0 の 2 スロットはマスクに入れない——歩行は固定された開始位置から走るので、マッチ全体は歩行の開始位置で始まり accept で終わり、その組は歩行自身が書く（`onepass_saves_span`）。捕獲なしの表はスロットを一切書かない。歩行は呼び出し側のスロットに直接書く。単一前進パス・~DFA 速度で記録。構築は 2 フレーバー：*uncut*（完全 accept 集合＝最長マッチエンジン。`e` で境界付けるか accept==n 条件で使う）と *leftmost-first cut*（各状態のクロージャを優先度順に探索し最初の `Match` で打ち切る。unbounded 歩行の最終 accept が leftmost-first 終端そのものになる。Alt 無し・貪欲のみのプログラム＝優先度順が pc 昇順のときのみ健全）。バイト毎のステップは**1 回の packed `u32` ロード**——次状態・スロットを書くかのビット・次状態が accept かのビットを 1 ワードに格納——で、別配列からの 3 ロード（依存チェーン上の 3 キャッシュライン）を置き換える。次状態は、状態の配列の中でのバイト単位のオフセットで持つ。ロードと次のロードのあいだに入るのはフラグのマスクと加算だけで、掛け算は無い（UUID の 5 つの群を取り出す検索：117 → 80 ns）。一部の ASCII バイトで自己ループしスロット書き込みの無い状態（`\S+`・`\d+`・`[^"]*` のような反復ラン）は、バイト毎の依存ロードでなく 1 回の SIMD 所属判定スキャン（`run_scan`）でラン全体をスキップ——状態*エントリー*時に一度だけ起動。ループ集合は構築時に 16 バイトの nibble 表（下位 nibble → 行、上位 nibble → ビット。2 回のテーブル参照で 16 バイトを判定、任意の ASCII 集合に対して厳密）にしておく：出口数の上限も呼び出し毎の出口リスト splat も無く、それが実データの主体である十数バイトのトークンで採算を取る鍵（出口集合 `scan64` ＋スカラ事前プローブ方式は、呼び出し毎のセットアップがスキップ分を上回って負けていた）。step 表は 256 エントリで非ASCII 側を dead にしてあるため、バイト毎ループに `≥ 0x80` 判定は無い。span 内に非ASCII コードポイントがあると中断（→ BitState）。 |
| **BitState**（`bitstate_bytes`） | one-pass でない・span ≤ `kBitStateCap` | 特定 span 上の `cp_prog_` を bounded leftmost-first バックトラック。コードポイントを逐次デコード（分割なし）、`(pc, バイト位置)` の visited ビットマップで O(prog × span) を保ち、キャプチャ書き込みは巻き戻す。 |
| **コードポイント Pike**（`cp_prog_` + `segment_cp` 上の `run_saves`） | span 超過、または DFA の断念でパターン全体が落ちたとき | 万能フォールバック。 |

全エンジンが同じ NFA 上で leftmost-first なので書記素エンジンと一致します。
（whole-match キャプチャ——全群=全体マッチ、例 `(\w+)`——はどれも使いません：
計画される時点で群がありません。§3「ルートのグループ」。）

**unbounded one-pass find（`cp_onepass_find`、`onepass_unbounded_`）。**
bounded 連鎖はマッチ毎に 3 回歩きます（前方 DFA で `e`、逆 DFA で `s`、その上で
capture エンジン）。AST に**選択肢が無く、lazy 反復が無く、反復下に捕獲グループが
無い**とき、テーブルは leftmost-first cut 付きで構築され、その下では固定開始位置
からの歩行の最終 accept が leftmost-first 終端**そのもの**になり（貪欲性だけでは
不十分：`x(?:ab)?(?:abc)?` のような隣接 nullable 反復は最長 accept より手前で
コミットする）、最終 accept 位置より後にスロット書き込みは発生しません——よって
マッチ**開始**さえ候補源から得れば、**1 回**の unbounded one-pass 歩行で終端と
全キャプチャが出ます。cut は pc の順に刈りますが、pc の順が優先順位の順と一致するのは
同じステップで分岐したスレッド同士だけなので、2 つの形を除外します
（`onepass_cut_ast_ok`）。ひとつは可変幅の本体を 2 回以上回せる反復（どちらの accept も
1 本のスレッドの経路上にある）。もうひとつは、複数命令から成るスキップ可能な反復で、
スレッドが異なる時刻に到達でき、かつその後ろに必須の要素があるもの——先に着いた
低優先のスレッドが反復の中に残り、後から着いて反復を飛ばしたスレッドより*低い* pc に
います（`[a-z]{3,}(?:\w{2}-)?s` は `hssys-s` 上で `[0,5)` でなく `[0,7)` を返して
いました）。ASCII tier の候補源は 2 つ：必須 ASCII
リテラル前置（`\{\{\s*(\w+)\s*\}\}`、`/users/(\d+)`。全マッチが前置で始まるので
最初に完走した候補が leftmost）と、非吸収 ReverseInner の床（`(\w+)=(\S+)`。床が
正確な開始）。失敗歩行のバイト予算が線形性を守ります（前置バイトを自身の反復が
吸収できる `a([a-z]+)0` × `aaaa…` は重なる尾を二次的に再歩行し得る）——予算切れは
located-span 連鎖へフォールバック。mustache `\{\{\s*(\w+)\s*\}\}` を
~0.69 → ~1.3 GB/s、markdown `\[([^\]]+)\]\(([^)]+)\)` を ~0.18 → ~0.52 GB/s
（いずれも rure 超え）、key=value を ~0.85 → ~1.1 GB/s に。`match()` も同じ歩行を
0 アンカーで使います。ドライバ群は 1 つの玄関（`onepass_driver_find`。どのドライバかは
プラン構築時に 1 回決めます：`Plan::walk_driver_`。リテラル前置 →
非吸収 ReverseInner → 位置スキャン。位置スキャンでは全位置が候補ですが、外れ候補は
たいてい最初のバイトで死にます——access-log ~0.13 → ~0.31 GB/s、RE2 超え）を通り、
唯一の assert が末尾 `$` のパターンも accept==n 条件でこの族に加わります
（`\.([a-zA-Z0-9]+)$`：73 → 50 ns）。

**anchored scalar-chain capture find（`chain_capture_find`、
`analyze_chain_capture`）。** one-pass 歩行のさらに一歩先：パターン*全体*が ASCII
リテラル文字と単一コードポイントクラス反復の連結で、固定の中間/端リテラルの周りの
パースがアンカー出現に対して**強制**されるとき、マッチも*全*グループも素朴なバイト
歩行から出ます——オートマトンは一切走りません。`(\w+)=(\S+)`：`=` を探し
（rare-byte / pair-probe スキャン）、`\w` を左へ、`\S` を右へ歩く；グループ span は
ランの境界そのもの。強制の条件：アンカーの左（右から左へ歩く）は、隣接要素の ASCII
集合が互いに素——または左の全要素が固定回数——で、各可変要素は `min ≥ 1` の貪欲、
かつ左のどの要素もアンカーバイトを消費できないこと（このとき歩行は先行するアンカー
出現を決して越えず、leftmost 開始が固定され候補の順序が保たれる）；アンカーの右
（前方へ歩く）は、各可変要素が後続と ASCII 互いに素（貪欲な最大ランがバックトラック
を要しない）で、最終要素は無条件（貪欲）；そして各キャプチャはちょうど 1 要素を包み、
全グループがカバーされること。候補近傍の非ASCIIバイトはオートマトンドライバへ
ベイルし、歩行は共有の失敗歩行予算を消費します（アンカー右の要素がアンカーバイトを
吸収し得るため、失敗候補は重なり得ます）。key=value `(\w+)=(\S+)` を
~944 → ~2160 MB/s に。

## 7. プレフィルタ

プレフィルタは「次にマッチが始まりうる位置は？」を、生バイト上の安い SIMD 向け
スキャンで答え、エンジンを候補でのみ走らせます。制約：**健全性**（偽陽性は可、偽陰性
は不可——各はプログラムから導出）、**線形性**（単一パス、候補ごと再シードなし）、
**外部依存なし**（`memchr`/`memcmp` ＋手書き NEON/SSE；高速プラットフォーム `memmem`
に依存しない）。

**スキャンループは1つ（`scan64` / `scan64_visit`）。** プレフィルタのバイトスキャンは
すべて同じ形——「`[off, n)` で 16 レーン述語を満たす最初のインデックス」——なので、
速いループは1箇所にだけ存在します：8ブロックのエントリーランプ（ヒット後に再開する
呼び出し元が、ヒット密度が高い領域では安い1ブロックコストで済む）、続いて1イテレー
ションあたり 16 バイト×4ブロック＋64 バイトごとに1回の any-hit テスト。停止なしの
スキャンを ~25 GB/s（libc `memchr`：16 バイト/イテレーション＋停止毎の call）から
~65 GB/s へ引き上げるのはこの 64 バイト/イテレーションで、このプリミティブで表現
されたスキャンはすべてそのレートを得ます。述語はプラットフォームのレーンマスクと
対応するスカラテストを供給する小さな struct（`PredEq`、`PredPair`、`PredInList`、
`PredSetPair`、…）で、**合成**できます：`PredOrNonAscii<P>` は任意のスキャンに
バイトパス tier の非ASCII停止を加えます（広げる述語のコピーは持たず、参照します。
作った直後の述語をコピーするだけで `[a-zA-Z]+ing` の時間の 4 分の 1 でした）。`_visit` 形は候補検証を*その場で*駆動——
検証はストライド内の各ヒットで走り、棄却された候補は次の ctz から続行（ループ再起動
なし）——なので、以下の候補+検証型プレフィルタ（`find_substr` の比較、`(?i)` fold
比較、融合 collapse 検証）は probe バイトが頻出でも偽陽性1つにつきビットスキャン
1回しか払いません。`find_substr_if` は呼び出し側の棄却条件を同じ検証に載せます
（assert tier の末尾 `\b`。ある文字の出現の大半はここで落ちます）。

**ニブル表のスキャン（`run_scan`、`word_start_block`）。** 任意の ASCII *集合*への
所属判定は、16 レーンの表引き 2 回（下位ニブル → 行、上位ニブル → ビット。
`PSHUFB`/`TBL`）で、集合の中身によらず厳密です。これらは `scan64` の隣に独立した
ループとして置いています（`scan64` のストライドは疎なプローブ向けで、表引きに要る
SSSE3 の実行時判定も持たないため）：`run_scan`（one-pass 歩行の自己ループのラン。
1 ブロック以内で終わるものが多い）と `word_start_block`
（WordOnePass の候補——本体の開始集合のバイトで、直前が語バイトでないもの——を
16 位置のマスクで返す。前のブロックの最終レーンを繰り越す。候補が稀な主題で
~14 GB/s、置き換え前の 1 バイトずつのループは ~3.4）。このマスクを受け取る find は、
先頭の 4 位置だけ先に 1 バイトずつ見ます（`word_onepass_find`）：マッチの直後は
次の候補が 1〜2 バイト先にあることが多く、予測の当たる分岐なら歩行はすぐ開始位置を
得られますが、マスクだとその計算を待たされるためです。

**どこで走るか。** DFA tier は前進スキャンの開始状態にスキップを畳み込む：まず
リテラル接頭 **memmem**（`find_substr`、`prefix_` / `byte_prefix_`）、無ければ
first-byte 集合スキップ。memmem は冗長でなく必須——非アンカー lf プログラムは
`(?s:.)*?` + 本体で、開始 ε-閉包に接頭の `.`（全バイト）が入るため first-byte 集合が
全バイト化しリテラル先頭パターンでは決して skip しない。memmem 無しだと pure-ASCII
subject のリテラル走査がバイト毎 DFA に落ちる（memmem を元から持つバイト tier より
≈7倍遅い）。単体プレフィルタは Pike フォールバック（後読み等）でも生きる。ディスパッチ
は排他：`dfa_ok_ && ascii` → DFA、それ以外 → Pike ＋ プレフィルタ。2系統は異なる
アルファベットで推論：書記素プログラム（`prefix_`、`first_bytes_.set`）は ASCII バイト上；
バイトプログラム（`byte_prefix_` 等、`byte_prog_` から）はバイト tier で任意 UTF-8 上
（自己区切りなので健全）。なお per-subject の byte-path ゲート（`first_nonascii`＝最初の
非ASCIIバイトへの SIMD 走査）は**呼び出しごとに1回だけ**計算し、`egc_byte_path` と
`ascii_grapheme_ok`（両者が precomputed index を取る）で共有する。ゲート毎に O(n) パスを
やり直さず subject を1回だけ分類＝でないと pure-ASCII の速いリテラル find はゲートが律速になる。

- **リテラル前置部分文字列検索（`find_substr`）** — **rare-byte トリック**。`memmem`
  は確実に速くない（macOS で ~1.3 GB/s の床）ので、代わりにリテラルの**最も稀な**
  バイトを `memchr`（英語散文頻度表 `byte_commonness` で選択：空白とよく出る小文字は
  高く、大文字は低く、数字・非ASCII・大半の句読点は稀で良い probe。散文に多い
  句読点——`,` `.` `"` `'` `-` と改行——だけは個別の値を持ちます。同じ表が後述の
  アンカー同士の比較にも使われるためです）し、候補をその場で比較して検証
  （`bytes_eq`：16 バイトまではインライン、それより長ければ `memcmp`。両脚とも
  `scan64_visit` 上を走る；依存ゼロ）。
  全 ASCII 前置（`prefix_.ascii`）は*任意*の UTF-8 subject で `memmem` スキップ可能。
  2 バイト以上の needle は**2バイト pair probe**（`PredPair`——rure の memmem の形）で
  走査します：needle の最稀2バイトが*両方*、needle 上の正確な距離で現れる位置でのみ
  停止し、2つの密度が掛け合わさって停止が一桁減ります（Sherlock corpus 上の `ing`：
  8033 → 2934）。コストはブロックあたり追加ロード1回。（頻度表が最稀バイトを頻出と
  言うときだけでなく、常に：表は英語の散文のもので、ほかの主題では「稀な」バイトが
  数バイトごとに走査を止めることがある——語列の上の `fox` は pair の 0.07 倍で、
  pair が散文に払わせるのは最悪 0.70 倍。）pair 距離には上限（48）が
  あり追加先読みがベクトルループに収まる範囲に留め、相方は**plan 時**に選びます
  （`pair_probe` → `probe2` フィールド群）——find 毎の再計算はマッチ毎に効いてくる
  ためです。
- **短い (?i) リテラル → ケース軌道の選択肢化（`decase_ascii_literal`）** — 純粋な
  印字可能 ASCII の `(?i)` リテラルで、全文字が *clean*（fold の前像が自分の ASCII
  大小文字のみ。live fold テーブルで判定）かつ cased 文字 ≤ 4 のものは、plan 時に
  明示的な case-sensitive 選択肢（`(?i)the` → 8 分岐）へ書き換えて `icase_` を落とす
  ——以後は通常のリテラル選択肢として Teddy/LiteralAlt tier が担う。軌道は icase
  リテラルがマッチするバイト列を任意 subject 上で**厳密に**列挙するので、下流の全
  tier が自動的に正しい。dense な `(?i)the` を ~0.73 → ~1.7 GB/s（rure ~1.4・
  PCRE2-JIT ~1.6 超え）。unclean な文字（`k`、`s`）や長いリテラル（`(?i)Sherlock`
  は 256 分岐）は下の前置 prefilter 経路のまま。cased 文字が無いリテラルは inert な
  `icase_` を落とすだけで素の Literal tier に乗る。
- **大文字小文字無視のリテラル前置（`find_substr_icase`）** — `IgnoreCase` でも
  全 ASCII 必須前置はフィルタとして有用だが、**ASCII subject 限定**。ASCII の
  case fold はそこでは厳密だが、UTF-8 上では fold 原像（Kelvin K→k、long-s ſ→s）
  が複数バイトで、バイト単位の fold 走査がクラスタ内部に着地し得る。よって
  `prefix_.icase` は前置が全 ASCII かつ非 US モードのときのみ立ち（前置は小文字化
  して保持）、*全ての*前置スキップ地点を分岐する。**ASCII subject** の地点（DFA scan、
  `pike_candidate`）は `find_substr_icase`——最も稀な**case-fold 後**バイトの
  両ケースを SIMD `memchr2`（小文字 `'s'` は頻出なので `'k'` を選ぶ）した後に ASCII
  fold 検証——を呼ぶ。`(?i)Sherlock` を ~1000 → ~8000 MB/s（≈ rure；RE2 ~440）に。
  **非 ASCII subject** ではバイト単位の fold 走査がクラスタ内部に着地し得るため、
  代わりに生 UTF-8 上で動く：**2 つの稀な case-fold プローブバイト**——*unclean*
  fold orbit から1つ、*clean*（単一バイト）orbit から1つ——を `memchr2` し、複数バイトの
  fold 原像（Kelvin `K`、long-s `ſ`、先頭バイトは `0xE2`）を取り逃がさないよう各々を
  刈り込み/ガードした上で、特定された窓を bounded anchored verify で確認する。候補開始は
  バイト first-byte 集合（`byte_first_bytes_.set`）で事前に刈り、orbit は `case_fold_groups()`
  由来。非 ASCII `(?i)Sherlock` を ~1035 → ~6316 MB/s（≈ rure 0.82×；従来は無フィルタ）に。
  両者とも健全：verify はエンジン自身の fold 対応マッチ。pair probe には `(?i)`
  版があります（`PredFoldPair`）：fast プローブの文字がそれでも頻出で（`(?i)Sherlock`
  の `k`）、*かつ* subject が前置の**どの**文字の fold 原像先頭バイトも含まないとき
  （`pair_leads` ガード——このとき全前置文字はこの subject 上で正確に1バイト）、
  最稀2文字の case ペアが前置上の正確な距離に並ぶ位置でのみ停止します。バイト距離が
  固定なので、ヒットは単一の候補開始を特定——窓歩行は不要。CRLF Sherlock corpus 上の
  停止 3681 → 771；`(?i)Sherlock` ~6.3 → ~8.6 GB/s、`(?i)Holmes` ~2.7 → ~9.0。
- **Teddy — SIMD 複数リテラル。** リテラル選択（`fox|dog|cat`）は単一前置を持たず
  first-byte スキップは毎 `f`/`d`/`c` で止まる。Teddy（Hyperscan / Rust aho-corasick の
  "slim" 設計。`Regex::Teddy`）は*全*候補の先頭 `N` バイト（fingerprint）をベクトル
  1 本ぶん同時に照合する。各 fingerprint は 8 個のバケット（1 バイトの 1 ビット）の
  どれかに属し、ブロックごとに fingerprint の各位置について `PSHUFB`/`TBL` のニブル
  ルックアップで「そのバイトがその位置になりうるバケット」を求め、連続する `N` バイトが
  同じバケットで一致した lane が候補になる。`N` は最短リテラルが許す最長 fingerprint
  （最大4）。
  - *fingerprint の出どころ。* プランの DFA が走らせるプログラム（`teddy_collect` が
    開始閉包を歩く）：ちょうど 1 バイトを取る命令が fingerprint を 1 バイト伸ばし、
    それ以外の命令に当たれば打ち切る。Grapheme モードでは ASCII 1 コードポイントの
    `Char`。CodePoint モードではプログラムが UTF-8 のバイトオートマトンなので、
    値が 1 つの `Byte`。だから同じ選択は両モードで同じ検索器を得る（人名 7 個、
    CodePoint：3.3 → 13.4 GB/s。lexer の演算子 9 種、search 1 回：25 → 12 ns）。
    CodePoint では fingerprint が非 ASCII のバイトでもよく（`café|naïve`）、数個の
    単一バイトからなるクラスは、バイトオートマトンがそれらの分岐として持つので、
    選択として読まれる（`[Hh]olmes|[Ww]atson`：1.2 → 12 GB/s）。
  - *fingerprint は 64 個まで。* 8 個を超えるとバケットを共有し、共有バケットは
    メンバーのニブルを混ぜた文字列も通す。`build` は fingerprint を頻度の高い順に、
    見積もった発火率（`byte_commonness`）の増分が最小のバケットへ配り、どのバケットが
    `shared`（fingerprint が 2 個以上）で、そのうちどれが `loose`（自分のもの以外も
    通す）かを記録する。それ以外のバケットの候補は fingerprint そのもの。共有バケットの
    候補は照合する（`confirm`）——どの fingerprint かを返す `find_print` では常に、
    位置だけを返す `find` では loose なバケットだけ。人名 16 個（`Sherlock|…|Stamford`）
    は DFA の 2.2 GB/s から約 12 に、キーワード 16 個は 0.87 から 3.3 に。
  - *走査。* ベクトルの型ごとに 1 つ——16 バイト（SSSE3、NEON）と 32 バイト（AVX2）。
    どれもブロックのルックアップを次のブロックへ繰り越すので、2 ブロックにまたがる
    fingerprint を読み直しなしで見つけ、1 ステップでベクトル 1 本ぶん進む（リテラル
    3 個・マッチなし：8.5 → 18 GB/s）。最後の端数ブロックは、重なり合うワード読み
    からゼロ詰めで組み立てる（`tail_words`。スタックのバッファ経由のコピーは、短い
    主題のたびに store-forwarding の待ちを起こした）。6 バイト未満の範囲は同じ表で
    1 位置ずつ歩く（`scan_scalar`。SIMD の無い環境のフォールバックでもある）：
    レクサの演算子 9 種を 3 バイトのトークンに当てる search は 30 ns から 12 ns に。
  - *切り替え。* SSSE3（`_mm_shuffle_epi8`）は x86-64 ベースライン（SSE2）に含まれず、
    AVX2 はどの環境のベースラインでもない。素の `-O2` Release はどちらも定義しない
    ので、以前は無言で scalar の走査に落ちていた——リテラル選択パターンで ~10–18× の
    崖となり、既定の Linux ビルド全てが踏んでいた（macOS は NEON、cl.exe は SSSE3
    ベースラインを仮定）。走査は `target("ssse3")` / `target("avx2")` を付けた関数
    （`scan_ssse3`、`scan_avx2`）に置き、キャッシュ済みの実行時判定（`cpu_has_ssse3()`、
    `cpu_has_avx2()`。`__builtin_cpu_supports`、`REGEXLIB_SSSE3_DYNAMIC` /
    `REGEXLIB_AVX2_DYNAMIC` tier）経由で呼ぶので、SSE2 ベースラインでコンパイルされ、
    CPU が対応していれば動く——ビルドフラグ不要。AVX2 向けのビルド（`-mavx2`、
    `-march=native`、`/arch:AVX2`）は 32 バイトの走査をコンパイル時に選ぶ。
    `REGEXLIB_DISABLE_AVX2` で 16 バイトの走査に、`REGEXLIB_DISABLE_SSSE3` で scalar の
    走査に固定できる（特殊なツールチェーン / A-B 計測）。同じ切り替えの形を
    `scan64_visit` にも試したが、**計測のうえ不採用**：属性付きのラッパーは
    ベースラインの呼び出し元へインライン展開できず、走査を外に出すと呼び出し元との
    融合（probe と verify が 1 つのコンパイル単位になること）を失い、VEX の得より
    損が大きい——`scan64_visit` のコメントを参照。その分はホスト向けビルド
    （`-march=native`、`REGEXLIB_ENABLE_NATIVE`）が得る。
  - *マッチャとして。* **全**候補が完全な ASCII リテラル（共有前置だけでなく——
    `analyze_literal_alternation` → `literal_alt_`）のときは、Teddy は prefilter では
    なくマッチャそのものになる：`literal_alt_locate` が `find_print` の返す
    fingerprint を取り、それで始まるリテラルを選択順に試して（`literal_alt_` は
    fingerprint ごとにまとめて並べてある。`literal_alt_at_`）、span を **DFA 検証なし**で直接返す
    ——純リテラル選択 tier。両モードで使う（`literal_occurrence_ok`）。Grapheme モードではグラフェム境界チェック
    （`literal_boundary_ok`）でどの subject でも健全、CodePoint モードのマッチは
    バイト列そのもの。短リテラルの比較はインライン `bytes_eq`（libc
    `memcmp` の *call* が tier の ~20% だった）。
  - *開始スキップとして。* *混在*選択（素のリテラルでない枝を含む）では、Teddy は
    lazy DFA の開始状態、one-pass 歩行の位置走査（`scan_onepass_find`）、書記素 Pike の
    候補発見器になる。開始状態が何で読み飛ばすかは
    プログラムの系統ごとに 1 回決める（`StartSkip`：リテラル前置、Teddy、小さくて稀な
    先頭バイト集合、なし）。Teddy は先頭バイト集合より常に優先——見積もりでは
    選ばない。歩行の位置走査と Pike の候補も同じ規則で取る（`scan_skip`。
    アンカーの値付けもこれを読む）。集合に何を求めるかは読む側が言う
    （歩行は小ささだけ）。Teddy はマッチが始まりそうな所で止まり、その速さは主題に
    よらない。先頭バイトの走査が速いのは、主題の中で稀な 2〜3 バイトのときだけで、
    稀でなかった場合は数倍遅い。
- **first-byte（dead-byte）スキップ** — リテラル前置の先頭 first-byte *集合* への
  一般化（`analyze_first_bytes` が開始 ε-閉包から収集）。`skip_to_first_byte` は集合
  サイズで階層化（1 → `memchr`；≤8 → NEON/SSE2 スキャン；それ以上 → 表引き）、
  `first_bytes_.sparse`（≤32）でゲート：密な集合（`\w` ≈ 63 バイト）は稀にしか発火
  せずオーバヘッドだけなので、何も払わない。遅延 DFA の開始状態がこのスキップを使う
  のは、集合が小さいうえに**稀**でもあるときだけです（`dfa_skip`：集合のバイトの
  `byte_commonness` の合計が基準以下）。スキップが 1 回止まるコストは、DFA が
  十数バイト進むコストに相当します。よく出る文字の小さな集合は数バイトごとに止まる
  ので、キーワード 16 個の先頭文字ではスキップありが 280 MB/s、DFA だけで進めると
  860 MB/s でした。基準（`dfa_skip_bar`）は、スキップの中の走査の種類で変わります。
  表で走査する集合（9 バイト以上）は 72 パーミル（約 45＝大文字全体ではスキップが
  1.6 倍速く、85 付近で並ぶ）。SIMD で走査する 1〜8 バイトの集合は 172 から 116
  （3 文字なら 144 パーミルでもまだ得で、195 では損）。
- **非ASCII subject での ASCII 前置スキップ** — 書記素 Pike に乗る非ASCII subject も、
  パターンが全 ASCII 必須前置を持てば恩恵：`prefix_skip_nonascii` が生 UTF-8 上で
  `find_substr` を走らせ書記素境界ガードを掛ける（`/Sherlock/` 崖除去の一部）。
- **必須接尾リテラルスキャン（`suffix_find`）** — リテラル前置の鏡像。いちばん良い
  手がかりが**末尾**にあるパターン向け：固定長本体の後に固定 ASCII リテラルで*終わる*
  形（例 `[a-q][^u-z]{13}x`。クラスで始まるので DFA の first-byte skip は密で無効、
  末尾 `x` は稀）。前方 DFA は
  全バイトを舐めてしまうので、代わりに稀な接尾を `find_substr` する。リテラルは
  **種であって答えではない**：ヒットは開始の*床*を復元する（接尾からの逆 DFA スキャンを
  非重複下限で floor）が、末尾は常にそこからの anchored **前方** DFA で取り直す——貪欲な
  可変長本体はリテラルをマッチ中間に置き得る（`singing` 内の `...ing`）ので、末尾を接尾から
  読むと切れてしまう。前置が*固定長*（`analyze_byte_suffix`）なら各接尾出現は一意の
  leftmost-first 候補になり、memmem カーソルは失敗候補を越えて進むが floor は据え置くので、
  失敗候補より前で始まるマッチも後続の接尾で拾える。*可変長*前置（`suffix_.var_pre`、
  rure の *ReverseSuffix*）は `[a-zA-Z]+ing` 等へ拡張するが、本体が **step-1 prefix-closed**
  （無限反復下の単一コードポイント atom）のときに**限る**。一般の可変長前置は leftmost-first
  を壊す：より長いマッチが先行する接尾ヒットの左で始まりつつ後続の接尾で終わり得る（fuzzer が
  `(?:[^a-c].\w+)?b` で正解 `[0,4)` でなく `[1,2)` を採用するのを捕捉）ので、それらは素の DFA に
  フォールバック。他と違い **DFA tier 上**（find_all/find_iter/search）で動き、capture 無し
  限定。リテラル前置も持つパターンは両方のアンカーを差し出すことになり、どちらで
  駆動するかは後述の*アンカー選択*が決めます。`[a-q][^u-z]{13}x` を
  ~57 → ~1650 MB/s（RE2 ~260；rure はより平坦な verify で ~12000）、`[a-zA-Z]+ing` を
  ~258 → ~1640（RE2 ~389 超え）に。残りのギャップは2つの改良で閉じます。
  (1) **scalar forced-parse 検証**（`Verify::Scalar`、`analyze_suffix_scalar_verify`）：
  接尾前の本体が ASCII リテラル文字と単一コードポイントクラス反復の鎖で、その
  パースが*強制*されるとき——隣接しうる要素対のバイト集合が互いに素（直接の隣接、
  および `min=0` 要素は空になり得るので空要素を跨ぐ推移閉包まで）、または全要素が
  固定回数（位置だけで配置が強制される）——各候補を逆DFA＋前方取り直しのペア
  （各 ~2.2 ns/B）でなく素朴な表引き歩行（~0.3 ns/B）で確認します。`absorb_last` は
  `[a-zA-Z]+ing` の形——クラスラン内の**最後**の出現がマッチ終端（重なり周期性の
  論法で強制される）——をカバー。候補近傍の非ASCIIバイト（collapse tier では CR/LF
  も）はその候補1つだけを DFA 検証へベイルします。(2) **class-tail アンカー**
  （`suffix_.cls`、`PredSetPair`）：アンカーはリテラルでなくてもよい——パターン*末尾*
  が2つの固定小クラス（`["'][^"']{0,30}[?!.]["']`）なら、クラスペアの隣接として
  スキャンします。2クラスは**互いに素**であること：重なるペアはアンカーの1バイト
  スライドを許し（`[ab]+[bc][cd]` は `abcd` 上で切れたマッチを報告してしまう）、
  admission は chain-or-nothing——scalar 検証の条件が成立必須で、DFA は候補ごとの
  ベイル先専用。CRLF corpus 上の引用文字列 ~1.25 → ~2.5 GB/s。
- **希少な中間リテラル（`ReverseInner`）** — 稀な固定リテラルが**中間**にある
  パターン向け（`\w+ Holmes \w+`、`\w+@\w+`）：両端に使える手がかりが無いと DFA は
  skip を持たず全バイトを舐める。中間リテラルを
  `find_substr` し、前置を逆 DFA で走らせて開始の床を復元し、そこから通常の lf 前方＋逆を
  走らせる。接尾スキャンと同じ **種であって答えではない**規律：末尾は床からの全体前方パスで
  取り直す——貪欲な前置が中間リテラルを飲み込み得る（`.{2,}c\d?`）ので、スパンをリテラルから
  読むと誤る（*singing* バグの inner 版——fuzzer が捕捉）。リテラルを吸収できる pre は、
  接尾スキャンと同じゲート（step-1 prefix-closed）も満たす必要があります
  （`find_inner_run`）：床は reverse(pre) が成功した*最初の*出現から取るので、pre の
  長さに隙間があると、それが吸収された出現で、床が leftmost マッチより右になり得ます
  ——`(?:..)*=x*` は `a==` 上で `[0,3)` でなく `[1,2)` を返していました。
  `\w+ Holmes \w+` を ~386 → ~10300 MB/s、`\w+@\w+` を ~275 → ~21400 に。（中間ギャップを持つリテラル*選択*
  `Holmes.{0,25}Watson` は既に発火する Teddy に委ねる。）capture パターンも許可する——
  prefilter はスパンの**位置特定**だけを行い、グループは capture エンジンがその上で
  解決する——ただし **pre が単一ノード**（`(\w+)=(\S+)`）の場合のみ：capture 連鎖は
  どのみち確定スパンを再走査するため、pre 部が長いと追加の reverse(pre) パスが密マッチで
  純損になる（7 グループの access-log パターンはこのゲート導入前に回帰した）。
  `(\w+)=(\S+)` を config コーパスで ~285 → ~830 MB/s（RE2 ~310 超え）に。
- **アンカー選択（`plan_anchor`、`AnchorChoice`）** — パターンは最大 3 つのリテラル
  アンカー（必須の前置、必須の接尾、中間リテラル）を差し出し、find を駆動するのは
  そのうち 1 つです。以前は位置の順で決めていました（前置があれば他の 2 つは無効）。
  `Sherlock\s+Holmes` には正しく、頻出の文字の後ろに稀な文字が来る形には 23〜90 倍
  間違っています：`e[a-z]{3,}q` は subject 中のすべての `e` を検証し（~0.4 GB/s）、
  クラス始まりの双子 `[eE][a-z]{3,}q` は `q` を探していました（~34 GB/s）。今は
  **見積もりコスト**で決めます。各アンカーを `byte_commonness` から
  「*停止回数 × 停止 1 回のコスト ＋ 出現回数 × そのアンカーに必要な検証のコスト*」
  として値付けし（`literal_cost`。散文 1 MB あたりの ns。単一 probe は最稀バイトの
  出現ごとに、pair probe は最稀 2 バイトがその距離で並ぶ所でだけ止まる）、次の規則で
  選びます。
  - 前置が現職です（その出現がそのままマッチ開始になる）。他のアンカーが 2 倍以上
    安いときだけ譲ります（`kPrefixBias`）。
  - **密な**前置（見積もり 1 ns/バイト以上、`kDenseNs`）には守るものがありません：
    より安いアンカーがあればそれに、無ければ融合 prefix tier を飛ばして走査に
    任せます——非アンカーの DFA はすべての出現を 1 パスで通りますが、出現ごとの
    先頭固定の検証は前の検証が読んだ範囲を歩き直します（`a[^.]*!` のような本体は
    走査の半分の速さでした）。
  - クラス始まりのパターンは、接尾／中間リテラルを自身の開始集合と比べ、集合の
    ほうが稀なら走査を取ります（`[A-Z][a-z]+s`：大文字は `s` より稀。
    ~0.55 → ~1.4 GB/s）。リテラル選択で始まるパターンは、走査が読み飛ばしに使う
    ものの値段で比べます——Teddy 自身の速さ＋見積もった候補数（`teddy_cost`、
    `kTeddyScanNs`）。
  - キャプチャがあるときは前置優先のままです：one-pass のキャプチャドライバが前置を
    候補源に取り、同じ歩行でグループも出すためです。

  `suffix_` / `inner_` は選ばれたアンカーのときだけ有効なまま残るので、階段の
  段は選択があったことを知らずにそれを読みます。記録は各アンカーのコストを保持し、
  テストはそれを通して選択を固定します（`PlanProbe`）。**assert tier** も先頭
  リテラルと末尾リテラルを同じ方法で選び（`plan_assert_anchor`。こちらは以前は
  接尾優先だったので、`Sherlock [a-z]+e\b` は `e` を探していました：
  ~0.35 → ~30 GB/s）、選んだアンカーと語スキャンの順序も決めます
  （`wop_after_anchor_`：`\bq[a-z]+e\b` は `q` の memchr で ~29 GB/s、語スキャンは ~14）。
  Sherlock corpus での効果：`e[a-z]{3,}q` ~0.4 → ~34 GB/s、`a.{16}z` ~0.4 → ~35、
  `a[^.]*!` ~0.33 → ~9.3、`s[a-z]*\?` ~0.67 → ~16——いずれもクラス始まりの双子の
  数パーセント以内です。

one-pass のドライバは
1 つの入口（`onepass_driver_find`：リテラル前置 → 非吸収 ReverseInner → 位置スキャン。
全位置が候補で、外れはほぼ先頭バイトで死ぬ——access-log ~0.13 → ~0.31 GB/s、RE2 超え）
を通り、唯一の assert が末尾 `$` のパターンも「accept==n」条件で同じ族に乗る
（`\.([a-zA-Z0-9]+)$`：73 → 50 ns）。
- **assert tier 固定text リテラル** — assertion パターン（`(?m)^X`、`X$`、`^X$`、
  `\bX\b`）は assertion DFA が担うが、これは本来全位置を走査する。ゼロ幅 assertion を
  剥がした後が単一の**固定リテラル**（`fixed_text`、再帰抽出）になるとき、エンジンはその
  リテラルを `memmem` し、各ヒットを anchored assertion DFA で確認する（`assert_find_span` /
  `assert_byte_find_span` 共有）。`(?m)^Sherlock Holmes|Sherlock Holmes$` を
  ~229 → ~12700 MB/s（≈ rure ~8000；RE2 ~455）に。リテラルで*終わる*、または*始まる*
  assertion 本体は下の 2 つの prefilter が拾う（両方に当たるときどちらを使うかは
  上のアンカー選択）。使えるリテラルの錨が無いものだけ全走査のまま。
- **assert tier 必須接尾リテラル**（`assert_.suffix`、`analyze_assert_suffix`）—
  先頭リテラル prefilter の接尾版。固定長／1コードポイント反復の本体の後に固定 ASCII
  リテラルで*終わる* assertion パターン向け（末尾のリテラル文字の並び全体を取る：
  `t[a-z]+ly\b` はすべての `y` でなく `ly` を探す。~1.7 → ~5.2 GB/s）。
  assertion DFA は全位置を走査してしまうので、
  代わりに `assert_suffix_find` が末尾リテラルを `memmem` し、各出現を anchored assert
  スキャンで確認、可変長の開始を逆走査で復元する。さらに `\b \w{n,m} <lit> \b`
  （`\b\w+n\b`、`\b\w+ing\b`）という厳密形には **DFA を一切使わない**語スキャン高速形：
  リテラルを `memmem` し、末尾 `\b`（次のコードポイントが非word）をスキャンの中で確認し
  （`find_substr_if`。`assert_suffix_find` の安い棄却も同じ）、word コードポイント
  を左へ歩いて run の開始を求め（`assert_word_find`）、`\w` の run 長が `{n,m}` に収まるか
  検査する。assert tier は単一コードポイントクラスタ（コードポイント == グラフェム）しか
  扱わず、ここの `\w` は素の Word 述語ちょうどなので、この歩きは正規表現を再現する（健全）。
  `\b\w+n\b` を ~190 → ~1,100 MB/s（rure/RE2 超え）に。
- **assert tier 先頭リテラル**（`assert_.prefix`）— assertion パターンが固定text では
  ないが**最初の消費アトム**が固定 ASCII リテラル（その前はゼロ幅 assertion のみ：
  `\.([a-z]+)$`、`^foo(\w+)`、`\bID(\d+)`。先頭のリテラル文字の並び全体を取る）の
  とき、全マッチはそのリテラルで始まるので
  リテラルの `memmem` が全候補開始を与える。続いて **anchored** assert 前進スキャンが
  マッチ全体（先頭+末尾の assertion）を検証し可変長の終端を返す。固定text/末尾リテラル
  prefilter と違い**capture-free に限定しない** ―― assert-capture tier(2a) の位置特定も
  駆動するので、`\.([a-z]+)$`（capture）も `\.[a-z]+$`（capture-free）も位置ごとの assert
  走査を回避（EGC ~640/~515 → ~220/~90 ns）。memmem 順＝開始順、全マッチは prefix で始まる
  ので最初に検証成功したヒットが leftmost-first。
- **純リテラル find の単一パス化** — 素の printable-ASCII リテラルパターン
  （`literal_only_`）は従来*2*パス払っていた：バイトパスゲート用の subject 分類、そして
  `memmem`。printable ASCII は `Grapheme_Cluster_Break=Other` なので、リテラルヒットが偽の
  クラスタ境界になり得るのは局所判定可能な2通りだけ（直前の `Prepend`、直後の
  `Extend`/`ZWJ`/`SpacingMark`）。リテラル tier はそれだけを判定して subject 全体分類を
  飛ばし、**単一**パスでマッチする。`zqj` を ~20000 → ~38600 MB/s、`/Sherlock/` を
  ~13500 → ~23800（RE2 超え）に。同じバイト単位リテラルプリフィルタは **UnicodeScalar**
  モードにも配線済み——従来は EGC 限定で、US `zqj` を ~450 MB/s に留めていた欠落穴。
  tier そのものは両モードで使う：針はバイトプログラムの先頭リテラル（`byte_prefix_`。
  パターン全体であることは `plan_literal` が確かめる）、ヒットに求めるものは選択 tier と
  同じ問い（`literal_occurrence_ok`）——Grapheme モードではクラスタ境界、CodePoint モードでは
  何も求めない。CodePoint では従来このリテラルは DFA 走査の開始スキップだった
  （散文の `Holmes` 20 → 33 GB/s、`the` 1.5 → 2.1。3 バイトのトークンの search 29 → 18 ns、
  60 バイトへの `test()` 52 → 18）。

各プレフィルタは正しい scalar フォールバックを持ち、ディスパッチは排他なので、どの
プレフィルタを無効にしても速度が変わるだけで結果は変わりません。

## 8. 結果の引き渡し：`search`/`find_iter`/`find_all`

マッチが*どこにあるか*（上のエンジン）と、結果を*どう引き渡すか*は別問題。API は
アリティと遅延性で分かれます:

- **`search()` / `match()`** — 1マッチ。自己完結の所有 `MatchResult`（マッチ文字列＋
  群文字列をコピー）。1回のコピーは安く寿命安全で、所有コピーのコストは bulk でのみ
  効きます。
- **`find_iter()`** — *遅延* bulk。`MatchIter` レンジがエンジンを **`++` ごとに1マッチ**
  進める（スレッドの warm DFA を再利用）ので、早く抜ければ残りは走査しません。各
  反復は `Match` の **view**（オフセット＋subject への view、保持は
  `to_owned()`）を yield、次の `++` まで有効。一時 subject は拒否（view が dangle）。
- **`find_all()`** — *先行* bulk。`Regex::MatchList` columnar コンテナ：全マッチを先に、
  バイトオフセットの Structure-of-Arrays（`SpanRows`：`uint32_t` のセル、マッチごと
  `2*(ngroups+1)` 行）＋subject バッファ1個として保持；`str()`/`group()` は `Match`
  プロキシ経由でそこへの `string_view`。ランダムアクセス・`size()`・複数パス可。
  行のセルは書かれないまま渡され、ブロックは `realloc` で伸びます（その場で伸ばすか
  再マップできる）：`std::vector` では倍々の再確保のたびに新しいページへ移り、書く前に
  ゼロ埋めもされ、密なマッチではそれが呼び出しの 4 割超でした（glibc での計測）。

両 bulk 形式は **view ベース**——マッチごとの `std::string`/`std::vector` 確保なし。
（所有 `vector<MatchResult>` は `find_iter()`/`find_all()` ＋ `to_owned()` で得る。）これは
意図的：密 `\w+` のプロファイルで、オフセットのみのスキャン自体は既に RE2 を上回る
一方、マッチごとの実体化（確保＋重い 120 バイトオブジェクトの vector 再確保）が実行
時間を支配していました。columnar コンテナはオフセットのみのスキャン速度（密マッチで
所有 vector の ~2.7×）・~15× 省メモリで走ります。

### 共有ステッピング

どの形式も、受け皿が違うだけの find の階段です（§2「find の階段」）。`search()` と
`test()` は 1 ステップ進みます（`find_once`：その場で組み立てる `MatchResult`、または
何も残さない）。`find_iter()` は走査（`Finder`）を保持し、`++` ごとに 1 ステップ、
1 行ずつ進みます。`find_all()` は同じステップを「最後まで」として呼び、行を追加
します。`find_at()` は、ある位置へ移した走査の 1 ステップです。走査の途中で DFA が
断念した段（§2「DFA キャッシュの予算」）は、現在のカーソルから Pike VM に降格して
続けます。

### 呼び出し間 DFA 再利用（`FindCache`）

そうしないと各呼び出しが `LazyDfa` を毎回ゼロから再構築します——`\w+` の全 Unicode
バイト DFA は構築 ~4 ms なので、1つの `Regex` で多数の小文書をトークナイズすると毎回
同じ状態を再発見します（ベンチで 1 文書 ~57 vs 8000 小文書 ~11 MB/s——5× の差は
*スキャン*でなく*構築*）。**呼び出し側が持つ `FindCache`**（PCRE2 `match_data` /
Hyperscan scratch / `regex-automata` `Cache` のイディオム）が DFA を呼び出し間で保持
します:

```cpp
class Regex::FindCache {       // opaque。テキスト非依存の状態のみ保持：
  const Regex *owner_;         //   DFA 遷移表 ＋ Scratch 容量
  std::optional<LazyDfa> ...;  // （セグメント化はテキストごとでキャッシュしない）
  Scratch sc_;
};
MatchList find_all(std::string_view, FindCache&) const;
MatchIter find_iter(std::string_view, FindCache&) const;
```

キャッシュなしの `find_iter(s)`/`find_all(s)` は、プロセス一意の `Regex` id で束ねた
**`thread_local` キャッシュ**を再利用します（id は生アドレスキーの ABA ハザードを
回避——破棄された `Regex` のアドレスが再利用されても id が違うので stale DFA は出さ
ない）。`Regex` 内ミュータブルキャッシュ＋mutex（RE2 のモデル）は共有 `Regex` 上の
並行マッチを直列化するため不採用；ここのマッチは lock-free のまま、`Regex` は `const`
で共有可能です。**寿命/スレッド契約**：1 `FindCache` は1スレッドで（スレッド間では
共有しない）、束ねた `Regex` より先に破棄。1 つのスレッドの中では、複数の Regex に
使われることがあります（スレッドローカルのものはそうですし、呼び出し側が渡すものも
そうできます）。規則は 1 つです：**キャッシュ済みの DFA を読む段は、自分の Regex に
束ねられたキャッシュの上で走る**。呼び出しをまたいでキャッシュを持つ走査（`Finder`）は、
そういう段に届きうるステップの最初に毎回、1 か所で束ね直します（`Finder::scratch`）。
1 ステップの find は `thread_cache()` から、束ねられた状態で受け取ります。DFA が
断念したキャッシュ（§2「DFA キャッシュの予算」）は、その DFA の次のミスで後退し
続けるだけです——正しく、そこから先が非加速になるだけ。

`MatchIter` は加えて**自身の** `Scratch`（Pike/backtracker 状態）を所有するので、
サスペンド点（`++` の境界で呼び出し側が同スレッドで他のマッチを走らせうる）を跨いでも
安全です：別の regex が共有キャッシュを束ね直しても、再構築のコストで済みます。
また、そういう走査が取得したスレッドローカルの表のエントリは、走査が生きているあいだ
**留め置かれます**（`Finder::Pin`）。この表は 1024 件を超えると追い出しを行い、残すのは
「いま呼び出されている Regex のぶん」だけです。これは同じ呼び出しの外側のフレームは
守りますが、ループ本体で別の Regex を 1000 個以上使うイテレータは守りません。（以前は
そのイテレータのキャッシュが解放され、次の `++` が解放済みメモリを読んでいました。）

## 9. 検証 — 信頼できる正解参照を持たない差分ファジング

正規表現エンジンには**出力の正否を判定できる外部基準（信頼できる正解参照）がありません**。
素直な参照——正しいと信じる別エンジン——が存在しないからです（`std::regex`
は標準ライブラリ間で文字列末尾の `\b` や複雑度上限が異なる；PCRE/RE2 は POSIX vs Perl、
Unicode レベル、空マッチ処理が異なる）。さらに、効くバグは**等価性バグ**——ベース
ラインと食い違うアクセラレータ——で、誘惑的なチェック（エンジン自身の別経路と一致を
assert）は罠：両者が同じディスパッチ・同じコンパイル済みプログラムを通るため**同じ
誤った前提を共有**しうる。

戦略（`test/regexlib_fuzz.cc`、固定 seed `0xC0FFEE`、ASan/UBSan 下で実行）は階層的:

- **層1 — 正解を知らずに検査できる不変条件ゲート（CI を落とす）。** ランダムなパターン/subject は
  クラッシュ/ハング/構築時 `RegexError` 以外の throw をせず、各マッチは自己整合：
  `m.str == subject.substr(m.begin, len)`（と各群）；マッチ時 `scan()[0] == search`；
  マッチは順序付き非重複；`test == search().matched`。これらは*正しいエンジンなら必ず*
  成り立つので、参照無しで検査できる。
- **層2 — DFA-vs-Pike 差分（実際に信頼する正解参照）。** 加速経路を、*同じ*意味論の書記素 Pike
  と照合。Pike はアクセラレータが見通せない変換で**強制**:

  ```cpp
  pike = Regex("(?=[\\s\\S]|$)(?:" + pat + ")(?=[\\s\\S]|$)");
  ```

  常真の先読み——次のクラスタは何でもよい、またはテキスト末尾——は全位置でマッチし
  何も消費しません。そして lookaround は、どちらの DFA 系もコンパイルしない
  構文です（`dfa_ok_`/`dfa_assert_ok_` が降りる）。そのためこの `Regex` は Pike で走り
  ——同じ全体 span にマッチする。後ろだけでなく前にも置くのは、Pike の段が素の VM
  ではないからです。まず候補まで読み飛ばし（リテラル前置、Teddy、先頭バイト集合）、
  そこで bounded backtracker を試します——入口は 1 つの階段を共有するので、どの
  入口でも。参照がこれらを使うと、Pike が受け持つすべてのパターンと同じものを共有
  することになります。先読みの後ろでは、どれも計画されず、VM は全位置から始まります。scan の全シーケンスを強制 Pike 結果と span 単位
  **かつキャプチャ単位**で比較。これが CRLF 健全性バグを捕えた検査：`gen_subject`
  は意図的に `\r` と `\n` を出し、CR-LF を1クラスタとして扱う*書記素*エンジンだけが、
  それを2と誤るバイトパスを暴ける。

  **強制できていること自体も検査します**（fuzz の `pike_reference`、単体テストの
  `pike_twin`。どちらも `PlanProbe` 経由）：参照のプランに加速 tier が 1 つでも
  あれば、あるいは Pike の段自身の加速（上記）が 1 つでもあれば、その実行は失敗です。以前は検査していませんでした。包みは
  `(?:PAT)(?:\b|\B)` で、「assertion があれば DFA 不可」だった頃に選んだものです。
  その後 assert tier が、まさに `\b` と `\B` を処理するために作られ、参照は黙って
  その上に移りました——検査対象の tier に、同じゲートを通って。その間、誤答が 2 つ
  隠れていました。両側が共有していた CRLF のゲート（`t[^.]+[^q]+\.` が `t\r\n.` に
  マッチ）と、CodePoint モードの multiline アンカーが CR-LF の内側で成立しない件
  （こちらは Pike と比べる層がそもそも無かった）。「アクセラレータが見通せない変換」は、
  その時点のアクセラレータについての主張です。成り立ち続けさせるには、プランに
  尋ねるしかありません。
- **層3 — US-vs-EGC。** UnicodeScalar は別のバイトオートマトン；照合先の正解参照は実証済み
  EGC エンジンで、**単一コードポイント・単一書記素**の文字（`a b 1 ␣ é ñ α β 日 A É Α`）
  だけの subject では書記素単位とコードポイント単位が一致するため有効。アルファベットは
  大小ペアを含み `IgnoreCase` 差分が畳み込みを行使（US はコンパイル時、EGC はマッチ
  時に畳む——一致せねばならない）。
- **層4 — 非ASCII assert バイト tier** を強制書記素 Pike と、multiline on/off で照合。
- **層5 — `find_iter` vs `find_all`。** 遅延 `find_iter()` の全シーケンスが先行 `find_all()` と
  一致（全 span・全キャプチャ）。2 つは同じ階段を上り、進め方が違います——`++` ごとの
  1 ステップと、「最後まで」と言われた 1 ステップ（その下では各段がその場で次へ進み、
  歩行は自分のループを持つ）。加えて **`FindCache` 再利用**チェック：subject 列に対し
  単一キャッシュ再利用 vs subject ごと新規が一致せねばならず、跨ぎ状態蓄積を守る。
- **入口が 1 つの階段を共有すると、検査が 1 つ減り、別の検査が要ります。** `search`・
  `test`・`find_all`・`find_iter` がそれぞれ自分のディスパッチを持っていた頃は、互いを
  比べることが 4 つの実装の突き合わせになっていました。いまは違います。共有している
  ものは共有しています。入口のあいだで違うものは狭く、名前が付いていて、それぞれの
  ための入力を引きます（`gen_ladder`、`gen_egc_onewalk`）：**真偽値**が使うときの
  プレフィルタの段（最初の受理状態で止まる。リテラルを含まない主題、1 回だけ含む
  主題、大文字小文字が逆の主題、本物のマッチの内側に結合文字を植えた主題）、
  **find** が使うときの 0 からの歩行（2 ステップ目は何も見つけてはならず、0 の
  空マッチが戻ってきてはならない）、EGC バイト tier の one-pass 歩行（CR-LF の対を
  1 要素と数えるクラスの中の対、非ASCII の文字だけからなるクラス、数キロバイトの
  ASCII の中の非ASCII 1 文字）。

`std::regex` 差分も保つが**情報用で決してゲートにしない**（意味論が標準ライブラリ間で
異なる）。実行するのは指定したときだけです（`regexlib_fuzz --std-diff`）：`std::regex` は
バックトラックするので、既定のシードでは 9 バイトの主題への検索 2 回（44 秒と 7 秒）が
fuzz の実行時間の 8 割、ASan では 17 分のうち 14 分を占めていました。可搬な意味論回帰コーパス（`regexlib_corpus`）は Python `re` で一度裁定して
焼き込み、実行時に参照エンジン不要。

**設計原則：** 保証は「多くのケースをテストした」ではなく、**各アクセラレータを、その
盲点を共有できないベースラインと照合する**こと——アクセラレータが悪用できない変換で
ベースラインを強制的に登場させる。アクセラレータを追加するとき、その固有の前提を
行使する入力で強制ベースラインと差分照合するまで完了ではない；自己整合チェックは代替
になりません。

## 不変条件（譲れない）

- **線形時間 / ReDoS 免疫** — 単一前進パス、逆クランプ、上限付きの DFA キャッシュ；
  無制限バックトラックなし。
- **全パターンで leftmost-first** — 順序付き+cut DFA は longest-safe 述語不要なので、
  どのパターン種別も黙って非 Perl な答えにならない。
- **書記素意味論が契約** — クラスはクラスタのベースコードポイントで判定；`.` は1
  クラスタ；オフセットはクラスタ境界。EGC バイトパスは純粋なアクセラレータで、
  `simple_from` / `simple_from_crlf_ok` でゲートし、さもなくば書記素 Pike へ後退。
- **各アクセラレータ == 強制ベースライン** — 差分ファザが常時保証（DFA、バイトパス、
  キャプチャエンジン、プレフィルタ、両 view コンテナ）、span **と**キャプチャを、
  生成 subject に CR/LF と大小ペアを含めて照合。
- **外部依存なし** — Unicode 表はヘッダに生成；プレフィルタは `memchr`/`memcmp` ＋
  手書き SIMD。
- **`Inst` は 16 バイト・trivially copyable** — クラスブロック出力とプログラム成長は
  `memcpy`。
